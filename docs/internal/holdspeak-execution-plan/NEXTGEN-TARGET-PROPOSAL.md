# HoldSpeak next-generation target proposal

**Status: product-led architecture proposal for review.** The owner has confirmed surgical evolution across frontend and backend, not a wholesale replacement platform. This document proposes a coherent destination and a strategy-level delivery outline; exact feature boundaries, navigation changes and module moves remain proposals. Detailed task planning is now authorized; executing those tasks is not. No code has been changed for this proposal.

Read [Product vision and journeys](PRODUCT-VISION-AND-JOURNEYS.md) for the confirmed purpose and [Decisions](DECISIONS.md) for the controlling chronology. Earlier Option C wording does not authorize parallel runtimes, a new stack or a broad cutover by default.

## 1 The destination is a coherent technical-life hub

A technical person should be able to take a project from intent through repository work and reviewed delivery. A technical leader should be able to connect priorities, people, meetings, evidence, decisions and follow-through across projects. Those two jobs—not the current folder tree or a framework preference—set the target.

The intended improvement is continuity: fewer occasions to reconstruct which project, repository, person, source or decision a piece of work belongs to; fewer competing entry points for the same job; and a clear next action with an honest result. This is a proposed experience, not a claim that every current transition is broken or that the new grouping has been validated.

A local feature change should have a discoverable owner, relevant contract and focused proof. Splits/moves are useful only when responsibility and change amplification improve. Large cohesive files remain acceptable; there is no line-count or file-count target.

## 3 Consolidate the experience without flattening the domain

Project context, repository/worktree location, a bounded task, a coordinating Program and an agent execution attempt are related but not interchangeable. Notes/Meetings are sources; extracted decisions, proposals and accepted canonical records have different meanings. Threads own conversation turns; detaching, requesting cancellation and persisted completion are different events. Preparing a send is not sending it, and an unknown delivery outcome is not safely retryable.

A coherent feature set should make these relationships easier to understand, not erase them or create a universal work-item schema. Preserve the applicable [domain invariants](INVARIANTS.md).

### What the recent evidence changes in this target

**Proposed priority, not accepted scope:** define the contract between existing evidence, current eligibility and the next effect before choosing module moves. The repeated pattern warrants common review questions, not one workflow engine or one universal state model. Three boundaries should guide the surgical design:

1. **Existing evidence producer → domain-owned eligibility.** The independently reviewed [human-review trace](NEXTGEN-JOURNEYS-AND-NAVIGATION.md#human-review-appendix-recorded-approval-versus-current-review-state-1500-follow-up) finds fresh approvals/changes already reaching PR receipts, while Program's latched `person_approved` skips later review checks during a wait. Review a policy for current eligibility versus historical approval, including head changes and unavailable reads. Reuse that receipt producer and once-per-review feedback rather than another polling subsystem. A failed read is not revocation, and internal eligibility is not proof that GitHub would permit a merge. Requirement evidence and human approval need not have identical semantics.
2. **User operation → retained identity across effects.** The [People Add trace](NEXTGEN-JOURNEYS-AND-NAVIGATION.md#director-commitment-recovery-one-add-spans-two-durable-writes-1530-follow-up) finds request creation followed by acceptance; a later Add creates a fresh ID after partial/uncertain completion. Same-ID acceptance is already atomic and replay-safe, and still-requested rows have the existing Asked-of-you recovery route. Review retaining an acknowledged request ID with submitted person/draft context and reconciling acceptance, while treating newer edits as a separate intention. Unacknowledged creation still needs an explicit uncertainty contract. An atomic create-and-accept command is an alternative domain change, not permission to erase the request/commitment distinction. Do not say “Nothing changed” merely because a later write failed.
3. **Feature composition → declared scope and authority.** Keep current membership distinct from provenance, project association distinct from obligation scope, and a prepared ordinary copy distinct from its private source. The existing queue, delivery, People and canonical-decision owners should expose their own known/unknown outcomes and supported transitions. A common screen must not invent one retry, Stop, Done or confidentiality rule for all of them.

These are design priorities and pending semantic choices. They do not choose new storage, commands, public APIs or folders. Module/interface work should make the responsible producer, consumer, authority and focused proof discoverable for a local change; file moves must demonstrate an improvement beyond renaming the same dependencies. No unwanted merge, duplicate commitment or runtime failure was reproduced, and no task expansion follows.

## 4 Frontend target

### One catalog and a direct navigation boundary

Source inspection establishes two different mechanisms today: a static application catalog with lazy module loaders, and a mount-order-dependent opener registry with pending/staged intents. The latter has real consumers and arrival/recovery behaviors. It is not accurate to dismiss it as merely static registration, nor to assume that every related behavior requires the current apparatus. See [navigation evidence](NEXTGEN-JOURNEYS-AND-NAVIGATION.md).

**Candidate target:** a navigation request names a known application/window and scope through the existing catalog; a small explicit startup/recovery decision decides whether to apply, defer or refuse the intent. Window rendering observes authoritative Desk state rather than needing to publish a generic opener after mounting.

This is a proposal, not a settled API. Before replacing the registry/queue, account for cold deep links, restricted recovery admitting Setup/Settings/Engines, alias scope, persisted-window reveal, conductor openings, invalid staged values and failure recovery. The compact Dictate override applies only to Dock-origin requests handled by `openCaptureOnPhone()`; preserve normal Go/verb/shortcut behavior. DrawerWindows is explicitly parked compatibility, whose continued need must be investigated rather than promoted into a current product requirement. Retain only the intent/state machinery required by those jobs. A replacement must be simpler in actual ownership and behavior, not the same queue under a different name.

The [HS-S12 conditional plan](stories/HS-S12-focused-navigation.md) now assigns those jobs to explicit transient admission/reveal state in the existing compositor, with one cohesive shell/host cutover and supported-caller gate. Proposed FIFO transient command application and the separate latest staged arrival still need G-OPEN approval; delayed Conductor restore means FIFO is not final-focus proof. Storage-failure fallback represents the same staged slot, with only current-runtime ordering guarantees. The existing exact proposal handoff remains unchanged.

**Lazy loading is a separate decision.** No bundle/startup measurements yet justify either removing or preserving every lazy boundary. Keep code splitting and failed/stale-chunk recovery only to the extent their benefits and behaviors are established. Removing opener registration does not imply eager-loading all features.

### Feature composition above shared material

The Desk shell owns windows, focus and layout. Reusable surface primitives provide controls, reading/editing/list patterns, feedback and accessibility. Feature/domain composition owns a workflow such as choosing a destination, previewing a send or reviewing a project concern.

The inspected SendWell dependency on Settings presentation/form code is a concrete candidate to straighten. Reuse the one admitted destination form rather than duplicate it. Place reusable domain composition where both Settings and Send can consume it without the lower-level surface depending on an application screen. Exact placement and public compatibility exports are still a review choice.

**Send placement: two options for review.** The [source-checked consumer map](STRUCTURAL-REVIEW.md#source-checked-appendix-send-and-destination-ownership) supports the existing `features/channels` family as a credible destination-domain home, not a home for all account discovery, onboarding, sign-in or calendar workflows.

| Option | Boundary and tradeoff |
| --- | --- |
| Narrow shared destination repair | Place the single form, cohesive draft/default helpers and destination-account warning adapter in the existing channels family. Settings and Send consume that domain composition; account contracts and state presentation remain below the Settings screen. This has a smaller compatibility surface, but Send remains an exceptional feature composition under `desk/surface`, not a primitive. |
| Broader Send composition relocation | Also place generic Send composition with channels, while document adapters retain their own identities and histories. This could make the feature owner easier to locate and avoids presenting the workflow as surface material, but affects more imports, lazy boundaries and CSS. The existing `features/channels/SendWell.tsx` is an update adapter, so a same-named file move is not a design. |

The existing [HS-S53 contract gate](epics/HS-E50-ownership-boundaries.md#hs-s53-destination-ownership-gate) now names the exact source/proof map and required dependency claim. Moving `DestForm` alone can retain the warning import through Send’s stateful barrel and the value import from `ConnectionsPane`; those paths must be removed or honestly retained, not hidden by a folder move. The gate is source/contract work only, with G53 and implementation pending.

Both options need a host-owned account-setup boundary: the current form searches Settings DOM and keeps its draft mounted, while inline Add supplies no alternate callback. Moving the file alone does not resolve that dependency. Settings listens for focus and account changes, clears failed account data and guards unmounts; inline Add listens to focus/manual retry and retains old data on error. A shared read must deliberately choose freshness and failure behavior, not silently inherit one host's behavior. Account readiness is channel-specific; a warning chip is not authorization.

Preserve one held-command store, tab-scoped pending identity/body/preview, replay and unknown-outcome semantics. Destination save is not send, and document allow-lists, meeting history and update-specific manual delivery remain with their respective consumers. Compatibility, migration and rollback should be proportional: account for direct and dynamic consumers, barrels, lazy-loading and CSS; retain only required old exports as aliases to the same implementation/store. A code rollback cannot undo a completed external send or safely turn an unknown outcome into a fresh retry. Review the architecture guard alongside the chosen dependency rule: its private-surface and roving checks cover `src/desk` consumers only, so moving a file must not merely evade enforcement.

For agent onboarding, compare both options using the same bounded change: can the agent find the form owner, host navigation/read contract, send custody and focused proof without reading unrelated Settings or document workflows? The narrow option keeps an exceptional Send location; the broader one has wider migration cost. Neither improvement has been measured, and neither option, exact path, compatibility plan nor implementation task is approved.

Do not mechanically migrate `pages`, `desk` and `features`. Define ownership first and make guards consistent across affected paths.

### Shared server reads without a second domain authority

Use the existing typed API and RuntimeBus boundaries. The hub remains the durable authority; the frontend coordinates reads and presentation. Existing `deskQueryClient` ownership is a candidate pattern for appropriate resource reads, not permission to migrate every hook at once or introduce another cache.

Preserve selected scope and newer edits across async work. A successful mutation acknowledgment must not be overwritten by an older read. Failed refreshes, failed saves and missing resources need truthful presentation without losing useful input/context. The original Program detail proposal is one local example; it is not the entire frontend target.

## 5 Backend target

### Boundaries follow responsibilities and real transaction ownership

HTTP, MCP and CLI adapters should obtain trusted context, validate/translate requests and call shared application behavior. Domain contracts need a discoverable owner; retaining service exports with a clear contract is a valid outcome, while moving definitions below orchestration must justify its compatibility cost. Runtime assembly/lifecycle should make the single installed object graph explicit; no second composition root or new dependency-injection framework is proposed.

Existing Python, React/Vite, Swift/native and device-runtime boundaries remain the baseline. The proposal makes no technology-stack substitution. Domain-local ownership can improve without forcing a monorepo-wide package migration.

A type-only import change would neither remove this collaboration nor establish compatibility with annotation introspection. Neither bounded AST pass executed application code or proves runtime independence.

G51 and exact paths remain pending.

Compare both against the **same bounded feature-change or onboarding concern**: can an agent find the owner, contract and proof with less unrelated context, and does a representative change touch fewer unrelated responsibilities? Neither gain has yet been measured. No new target path is selected. Existing `holdspeak/services/program_rules.py` owns control decisions, while `holdspeak/project_contracts.py` owns Project command vocabulary; their existence does not make either a catch-all home. No new service, package tree or microservice follows from these options.

The following constraints apply to either alternative:

- **Project transaction and effect ownership:** preserve `create_item_in_transaction` on the caller's connection, including Delta acceptance's idempotency, revision, item/change rows, ledger and kernel-completion coordination. Saved Ask and `mark_room_read` have different mutation paths. Preserve helper/decorator effects without missing or duplicating observation when delegating through a façade.
- **Program runtime and persistence ownership:** retain the same `_LOCK`, service instance, injected/default runner behavior, service-identity cache and thread-local `_held` coordination. The shared `RLock` is not a database transaction: text refusal can leave earlier changes written. A definition move must preserve that partial-write/error behavior, not promise atomic Program edits.
- **Helper selection:** `your_turn` reaches 25 top-level definitions; `_budget` calls `program_text`, which imports `triage_effort` back. `programs_on`, `_new_id` and `_seconds_between` involve environment, UUID or clock behavior. Do not sweep these into a “common” module or call the result pure without checking their actual dependencies.

### Persistence and recovery stay domain-specific

Preserve canonical schema/shape-based reconciliation, shared transaction support and each domain's repository semantics. Module moves do not require a new database. Prefer no storage/wire change when the job is responsibility cleanup.

A public Thread boundary may clarify persisted completion without merging automation and interactive lifecycles. A checkpoint projection may explain a missing restart snapshot without blocking a handoff or re-pinning history later. Memory's eventual enrichment with live admission/hash revalidation remains valuable. Channel unknown outcomes must retain durable uncertainty rather than acquire a generic retry. These constraints belong to their domains, not a new universal recovery engine.

## 6 Migration and rollback proportional to the change

The default is a surgical change in the existing system with one authoritative writer and one implementation of consequential behavior. There is no default parallel replacement runtime, dual-write scheme, global cutover or feature-flag platform.

- For a module/interface move, use only the compatibility exports/adapters needed by actual consumers. Preserve current callable names, refusal class identity and required import paths; aliases must reference one definition, not create duplicate classes, locks, default services or runner caches. Verify dynamic registries, external/public imports, annotation introspection, callback/decorator behavior and focused tests before retiring old paths.
- For a navigation mechanism change, prove equivalent required entry/recovery behavior before retiring the old registration path. Do not keep two independent navigation authorities permanently.
- For a UI consolidation, preserve access to current actions/results and scope. Navigation consolidation does not require merging underlying records.
- If an approved change genuinely needs a schema or wire transition, give it its own explicit compatibility/data-preservation/rollback design. Do not introduce such a transition merely to make the rewrite look comprehensive.
- Rollback must account for any durable state written by the new behavior; reverting code is not automatically sufficient. No reversal of already-sent effects or deletion of history is implied.

For the retained-façade alternative, rollback is limited to the contract/index edits because no runtime move is proposed. For a definition-only move, restoring the previous definition/import locations is proportionate only after proving unchanged wire/storage formats, identities and behavior; keep required compatibility exports until consumers are accounted for. An altered Project transaction boundary or Program partial-write policy is a separate behavioral change requiring its own review and rollback design, not an incidental cleanup.

Proof uses isolated fixtures/adapters, never duplicate live effects. Current worktree/test/shipping rules and separate live-operation authorization still apply.

## Startup navigation ordering before retiring registration (19:00 review)

**One unresolved compatibility choice:** when several scoped opens arrive before normal Desk readiness, does navigation retain only the latest destination, or replay every request in arrival order? Decide this before replacing opener registration. The existing two handoff paths do not implement one uniform answer. This is source-only evidence at `80b641fa41c7352280cfa52e933acf6dbe8d3857`, not a reproduced navigation failure or authorization to implement a change.

**New concrete distinction:** [`shell.ts:24–30`](https://github.com/karolswdev/HoldSpeak/blob/80b641fa41c7352280cfa52e933acf6dbe8d3857/web/src/desk/shell.ts#L24-L30) drains matching in-memory pending opens from the end of the array. By contrast, [`stageSurfaceOpen:47–54`](https://github.com/karolswdev/HoldSpeak/blob/80b641fa41c7352280cfa52e933acf6dbe8d3857/web/src/desk/shell.ts#L47-L54) overwrites one sessionStorage slot, retaining B when both writes succeed. ### Minimal alternatives

- **Replace registration with direct store calls alone:** removes the mutable opener map, but is not sufficient. The current registration owner also enforces recovery admission, leaves the staged intent untouched in recovery-only mode, and reveals persisted windows held off glass (`SurfaceWindows.tsx:94–159`). A direct call must retain those decisions elsewhere, or it changes the job. Lazy loading need not change.
- **One explicit latest startup intent:** closest to the successful stored-arrival path. Keep the pending destination and scope in the existing navigation/startup boundary, apply it only when admitted, and give storage failure the same ordering semantics. This is the smallest candidate if only the final arrival matters. A single global slot would discard requests for different destinations, so it cannot replace all in-memory callers without deciding whether those separate opens must survive. No new durable domain record or generic queue is justified by this evidence.
- **Explicit FIFO pending requests:** preserves distinct requested opens and makes the latest same-window scope final after replay. It retains more machinery and can perform intermediate opens, focus changes and persistence writes. Choose it only if those separate operations are required; merely preserving the current reverse drain is not a demonstrated compatibility requirement.
