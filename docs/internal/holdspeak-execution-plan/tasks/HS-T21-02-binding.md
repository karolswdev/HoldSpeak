## Implementation and proof

1. Add optional `origin_ref` to existing `PlanStep`, representing an existing backend input rather than a new API. In the existing Add flow, offer an explicit initially-off action-binding choice only for the loaded Program's recorded nonempty exact action origin. That reference is not proof of current source existence, status or eligibility; do not infer those from a board row or missing row. Show its source and consequence, allow Cancel with no request, and retain ordinary unbound Add for all other origins. Matching/ambiguous existing bindings suppress the new convenience, not delete or reassign existing data.
2. Submit only the new row through `planProgram(programId,[row],false)` in Drafting and running. Do not reconstruct existing steps. Prove old IDs, origin/gate values and step-local requirement IDs/links survive both bound and later unbound Add. The new convenience creates no history row and issues no extra Start/finish command. Disclose that appended work in a running Program can be scheduled under the existing lifecycle.
3. Guard the destructive bulk agent `onPick` for action-backed Programs or any action-origin row, including older From the Desk work. Explain the existing per-step agent edit. Preserve separate `onThen` and `onIdle` behavior; do not disable the whole picker just to protect one callback. Re-read current Program before a new bulk write and refuse the destructive path if the read is unavailable or the protected scope is present. A read-before-write is not CAS; disclose external/concurrent replacement limits.
4. Preserve existing `StepFold` per-step PATCH and origin immutability. Add a concise ordinary-text binding line in the shared StepFold presentation with the exact origin from acknowledged Program/step wire. Keep it visible when that fold is opened in planned, running/review and finished states; do not put it only inside conditional PlannedBrief or style it like an exact-action link. Do not add a new clickable source control in this bounded branch; preserve existing Program source controls unchanged. It describes which work is linked, not current source availability/completion, causal credit, an exact source destination or a new acceptance gate. Do not expose private People IDs or invent a fresh action-status endpoint.
5. Freeze the submitted Program/action/new-row tuple. Block duplicate local presses. On acknowledged response, use returned durable rows; on malformed response/generic failure, retain uncertainty and offer read/review rather than automatic re-POST. An acknowledged append followed by refresh failure remains an acknowledged append. Dismiss/unmount is not server cancellation; late results cannot replace a newer draft or force abandoned navigation. Do not reuse the generic 'step unchanged' message for an ambiguous append.
6. Add real producer assertions in existing from-action tests: create from action, append exactly one bound step, retain preexisting rows/requirements, and show a later ordinary append remains unbound. Capture only the two V21 response fixtures after semantic assertions. Keep existing project/repository/person behavior and no implicit provider dispatch.
7. Extend completion characterization in the owned existing tests, without changing runtime completion code: intended action/linked records and evidence, no-PR Done, non-trigger states/history, replay/dismissal, actor ordering/mixed modes/reopen and partial write failures. Tests must distinguish current limits from desired but unimplemented guarantees.
8. Extend app tests with real producer fixtures plus clearly labeled injected failures. Prove new control/default, captured body with `replace=false`, no bulk replacement in protected scope, functioning per-step edit and preserved separate picker commands, later Add/text visibility, stale/uncertain/late outcomes and no marker-derived completion badge. Implement the narrowly intercepted browser case in V21, then run final focused proof.

## Rollback and stops

Reverse the cohesive UI/type/style/test patch only after reviewing older-UI replacement risk. Never erase created steps, action completion, requirements or receipts to make rollback look clean. Stop for a binding request whose recorded action identity cannot be established from acknowledged wire, a required exact-action destination/current-state guarantee, unsupported widget behavior, missing proving harness, stale-state contract mismatch or a need to coordinate the two completion actors. Ordinary unbound/non-action Add is not blocked by the absence of an action origin. A requirement for a new destination or authority guarantee needs a new accepted scope, not a small silent fix.
