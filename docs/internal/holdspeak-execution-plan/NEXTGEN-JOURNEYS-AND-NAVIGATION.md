## 1. The frontend really has two separate mechanisms

1. **Static catalog and lazy code loading.** `web/src/desk/applications.ts:73` declares a readonly application list with literal module loaders. `SurfaceWindows.tsx:61–76` derives windows and wraps each loader in React `lazy(watchChunk(...))`. `runtime/freshBuild.ts:165–172` asks the build watcher to check after a failed chunk, then rethrows. This is code splitting/error recovery, not asynchronous plugin discovery. No bundle/load measurements were made, so a performance justification is not established.
2. **Runtime, mount-order-dependent opener registration.** `desk/shell.ts:15–74` keeps a mutable opener Map, an in-memory pending-open queue and a sessionStorage staged intent. `SurfaceWindows.tsx:146–170` registers openers/aliases in a React effect and publishes registration readiness. Registration flushes queued opens. This is real lifecycle complexity beyond lazy imports; calling the whole design “just a static registry” would be wrong.

The inspected use cases are cold/deep-link arrival before the Desk mounts, restricted first-use recovery (Setup, Settings and Engines keys), scope aliases and restoring/revealing persisted windows. `App.tsx:37` stages an arrival; normal SurfaceWindows consumes it, recovery-only mode deliberately does not. `shell.ts:81–98` also allows a mounted screen to intercept an action; `ChairDesk.tsx:143–144` uses that for Dictate only when the origin is the Dock and `openCaptureOnPhone()` handles it; Go/verb/shortcut retain normal Speak behavior. These are identifiable behaviors—not evidence that a generic registration mechanism is the simplest implementation.

**Proposed simplification:** a single explicit navigation command addresses a known application/window in the static catalog and changes Desk state directly. An explicit startup/recovery state decides whether an intent is allowed, deferred or rejected; window rendering observes that state rather than registering handlers after mount. Keep only the startup intent needed by actual route handoff. Treat conductor opening and the Dock-only compact Dictate override as named navigation cases, not a general plugin registration API, unless another real requirement emerges. DrawerWindows explicitly labels its key parked/legacy compatibility; validate whether that behavior is still required instead of promoting it into a current product requirement. This is a design candidate, not yet proven equivalent.

Do not conflate that removal with eager-loading every feature. Decide lazy loading separately from measured startup/chunk costs. Remove stale-build chunk handling only if its user-facing recovery requirement is met elsewhere or intentionally retired.

**Impact evidence:** a literal-spelling scan covered all 1,539 `web/src` TS/TSX files, including tests and parked paths. Non-test registration sites occur in `SurfaceWindows`, `ConductorWindows` and `DrawerWindows`; `shell.ts` defines it. `DrawerWindows.tsx:10–12` explicitly calls its key parked, with no product opener naming it: a compatibility site, not evidence of a current workflow requirement. `answerSurfaceFirst` has one nondefinition match, in ChairDesk. This is not a compiler reachability graph and does not certify parked code inactive. Results: `${ANALYSIS_ARTIFACTS}/frontend_registration_refs.json`.

Before changing the mechanism, preserve or deliberately revise: cold `/meetings` arrival, aliases plus scope, first-use recovery-only admission, persisted windows surviving reentry, conductor opens, Dock-only phone/compact Dictate behavior (without changing Go/verb/shortcut), invalid sessionStorage values and failed chunk recovery. Existing relevant tests include `desk/__tests__/shell.test.tsx:328–341`, `surface-windows.test.tsx:141`, `settings.app.test.tsx:139–140` and `features/project-room/door/__tests__/newProject.app.test.tsx:71`. These were located/read as source, not executed; they are not a claim of complete coverage.

## 2. Organize around two existing jobs

This is a proposed grouping of current capabilities, not a new feature commitment or a completed UX audit.

| Owner journey | Existing capability homes | Coherence proposal |
|---|---|---|
| **Build and deliver a project:** project/repository → goal/requirements → agent work → review/decision → delivery/recovery | `project_service`, `project_repository`, `repository_workspace`; `program_service`, `program_requirements`, `program_runner`, `program_audit`; agent delivery/terminal/PR receipt modules; Programs/Projects/Terminals surfaces | A project-scoped **Build & Delivery** workspace keeps project, repo, Program, active work, requirements and proof context visible across these steps. Shared navigation/context should remove repeated reconstruction without merging Program and Project state machines. |
| **Direct technical work:** priorities/people → meetings/evidence → decisions/commitments → follow-through → review outcomes | Project Room read model, People, meeting/session/aftercare, canonical decision and proposal services, steward/watch/update services, channels/Reach, briefing/needs-you | A **Direction & Follow-through** workspace presents decisions, commitments, risks and delivery evidence in the same project/person context. Meetings remain sources of evidence, not a competing destination where the chain ends. |

Cross-cutting capture, Ask/Threads, Memory and search should feed those jobs without forcing the owner to understand indexing, route plans, service registration or storage variants. Their internal ownership must remain explicit. The current implementation already has some links; this proposal is not a claim that the journeys are absent.

**Important separation:** merging feature sets or navigation does not merge extracted meeting decisions with canonical decision records, project-review proposals with user decisions, or owner authority with agent execution. Preserve source provenance, idempotency, revision rules and durable receipts while reducing the owner’s context switching.

### Three consolidation candidates for owner review

1. **One explicit work-creation context across existing entry points.** Project/action/note entry points carry their genuine context; the global entry asks for project/repository before creating. Alternative: a single chooser for every entry, simpler centrally but more repetitive for contextual work. A different product choice is to allow an unbound Draft and require repository binding before Start; that would change the backend lifecycle/preconditions, not merely fix navigation, and needs explicit validation, start prerequisites and migration analysis. Neither option is accepted yet. Do not silently convert a display filter into authorization or choose the first project.
2. **One explicit origin-to-completion rule.** Decide whether an action-backed Program fulfills its action at a designated step or only at accepted whole-Program completion. Keep informational “from” links distinct from completion obligations. Copying the origin onto every step is cheap but can close work prematurely; whole-Program completion must respect end requirements and applicable control-level acceptance rules (including owner acceptance when required).
3. **One current project overview for work already linked to it.** Surface the existing Programs projection in the current project journey, or provide an explicitly project-filtered transition into the existing Programs list. The former avoids context switching but adds visual weight; the latter reuses a focused surface but requires deliberate scope propagation. Neither requires a new app or a new source of lifecycle truth.

**Concrete decision:** is a Program repository-bound at creation, or may an unbound Draft exist until Start? The first option fits the current backend; the second requires a deliberate lifecycle change. Project-launched work should retain its explicit project/repository context either way. Once that interaction is agreed, backend contracts and frontend module ownership can follow it rather than drive it.

- **An existing launch retains source/worktree identity.** `LaunchService.launch` records `source_id` and `worktree_id` (`holdspeak/delivery/factory_launch.py:1440–1448`); restart resume resolves those IDs and refuses a missing worktree (`_worktree_path:1800–1813`, `resume_session:1856–1858`). That resume path does not look up the project's new repository. A fresh hand-off and resuming an existing launch must not be presented as the same repository-binding operation.

It does not rewrite Programs, move worktrees or retarget launch records. Registration requires an admitted operation and the owner (`AgentHandService.register_project_repository:731–746`); cloning and process launch remain separate effect boundaries.

**Source-derived example:** a Program created for Project X against repository A continues to use A after X is registered against B. This is a bounded lifecycle/selection distinction, not a reproduced wrong-repository incident. The inspected tests do not establish the composed reassociation scenario.

**Limits on “stable.”** The Program saves a path and branch name, not an immutable repository/commit snapshot. `DeliveryRegistry.register:325–375` validates the path as a Git worktree and matches its common-directory identity; it calculates a fingerprint for a new source, not a fresh comparison for every known source. This review does not establish behavior after external replacement of that directory or changes to its Git remotes. New worktree placement is server-derived from the selected source's primary checkout, with containment/name guards (`factory_launch.py::derive_worktree_path:536–549`); existing-worktree selection is constrained to that source and Hand again checks the prior item/worktree (`_resolve_worktree:1186–1257`). Preserve these boundaries rather than making a shared project selector an execution authority.

**Review implication:** show the actual bound/selected repository alongside project context and distinguish filing, changing the project's default association, and moving existing work. Whether waiting ordinary work should retain its earlier target or use a refreshed selection is a separate contract choice. No repository migration, new storage model, automatic rebind or implementation task is approved here.

## Dependent steps: readiness does not establish a fresh starting tree (14:00 follow-up)

**Same pinned snapshot, new source-only orchestration question:** when step B waits for step A to finish, which repository state does B actually receive? No application, Git operation or test was executed in this review.

`ProgramRunner._promote:521–527` makes a planned step ready when its `after` ordinals count as finished. This is a lifecycle condition. `ProgramService._ordinal_finished:1369–1373` also deliberately treats owner-parked predecessors as finished, so `after` cannot universally mean “all predecessor code was merged.” Preserve that existing distinction.

**The separate starting-tree contract:** `agent_hand_service.py::program_step_spec:182–205` sets a new step's start point to the Program's saved base-branch name, unless an explicit checkpoint supplies its pinned ref. `delivery/factory_launch.py:603–609` appends that literal start point to `git worktree add`. The default Program base is a branch name derived from `origin/HEAD`, not a remote-tracking ref or immutable commit (`program_service.py:5590–5603`). The launch records the worktree's resulting HEAD as `base_commit` afterward (`program_runner.py:937–944`); that records the selected state but does not itself make it current.

**Concrete conditional integration concern:** on the non-GitHub path, `_merge_local:2131–2162` fetches and rebases the predecessor's worktree onto `origin/<base>`, then pushes its HEAD to the remote base. That path does not advance the owner's local base branch. If that local branch still points to the earlier commit, a subsequent newly created step using the bare branch name starts there, even though its predecessor is now marked merged. The inspected promotion/launch chain does not resolve this difference. This is a source-derived starting-state mismatch under that condition, not an observed failed build or a claim that every successor is stale. The owner or an agent may update the branch separately; that is not an orchestration guarantee established here.

**Design boundary for review:** make a new step's selected base commit and its provenance explicit, distinct from the display branch name and readiness condition. Decide whether ordinary successor steps use a freshly resolved remote base or a deliberately fixed Program baseline; preserve explicit checkpoint starts and existing-worktree continuation. Reuse that selection in launch and its brief/evidence, and refuse or explain unavailable freshness rather than silently claiming predecessor integration. Updating the owner's checkout as a hidden side effect would be the wrong shortcut. This calls for a narrow repository-start contract, not a new scheduling framework or a requirement that owner-parked work be merged.

**Important successful integration evidence:** `tests/integration/test_program_execution_perfection.py:262–295` runs three sequential steps against a bare remote and verifies Done plus all three resulting files on the remote. This is real local-merge-path coverage, not absent integration coverage. Its nonoverlapping file changes can be combined by the later rebase; it does not assert that B's initial tree already contains A. `tests/unit/test_program_hand.py:19–64` explicitly checks the fresh worktree HEAD equals the local base (`:51`). GitHub ordering tests (`test_program_execution_perfection.py:45–89`; `test_program_run.py:66–107`) use a fake whose merge marks PR state without performing a Git merge (`program_rig.py:198–202`). These source-inspected tests establish useful ordering/result behavior, not fresh dependency input. **Existing mechanisms to reuse or preserve:** the final requirement worktree already fetches and selects `origin/<base>` (`program_runner.py:471–484`), as does final delivery (`program_delivery.py:213–226`); neither runs as the prerequisite-base selector for a new B. ## Director commitment recovery: one Add spans two durable writes (15:30 follow-up)

**Pinned snapshot `80b641fa41c7352280cfa52e933acf6dbe8d3857`; source-only finding, not a reproduced failure.** The unanswered question is whether retrying People’s “I owe <person>” Add preserves the identity of a partially completed operation.

## Oversight-to-project handoff: reveal the work without saving or accepting it (18:00 follow-up)

**Pinned snapshot `80b641fa41c7352280cfa52e933acf6dbe8d3857`; source and test code read only.** This is a verified continuity requirement for the proposed simpler navigation boundary, not another claim that the journey is broken.

**The current handoff preserves more than project identity.** A project-linked Needs You proposal row passes both project and proposal IDs (`NeedsDrawer.tsx:85–92`). [`openProjectProposal`](https://github.com/karolswdev/HoldSpeak/blob/80b641fa41c7352280cfa52e933acf6dbe8d3857/web/src/desk/openObject.ts#L95) records one pending target per project (the latest replaces an earlier pending target), opens the Room and signals it (`openObject.ts:95–109,145–150`). The Room consumes the target on mount or event, returns to its Room wing and selects that proposal (`ProjectRoomCore.tsx:2104–2113,2145–2157,2188–2199`). A local request sequence lets reopening the same target reveal it again; the scroll is consumed once when the selected row exists, so ordinary rereads do not repeatedly pull the user back (`:2260–2275`). The transient target deliberately does not survive a reload.

**Navigation is not consent to save the draft or accept the proposal.** When a proposal interrupts the update editor, `useUpdateController.stepAside:191–200` hides the posture and clears its saved location without saving or clearing the update, newer draft text or failure. Returning to the editor preserves that work. This does not cancel an explicit Save already in flight: it prevents the navigation gesture from initiating another update save/publish. It is not a claim of zero writes: Desk location state and Room read tracking can still change. Proposal acceptance likewise remains a separate Confirm action (`ProjectRoomCore.tsx:646–653`; `useProjectRoomController.ts:281–299`), which POSTs to the existing confirm endpoint (`api.ts:155–163`). Revealing a row does not accept its proposal or turn a saved update into an authorized send.

**Source-test support:** `desk/needs/__tests__/NeedsDrawer.test.tsx:1250–1284` mounts the overview and Room, then checks the exact proposal is selected with its Confirm control and no drawer opened. `project-room/__tests__/room.app.test.tsx:618–657` checks proposal navigation during pending/failed update saves, no extra PUT, and retention of newer unsaved text on return. `:661–724` checks reopening the same target from History/Update and repeated scrolling. These are inspected mocked UI tests, not browser execution, a complete reload/recovery proof, or evidence that every posture has identical no-write semantics.

### Alternative evaluated against the user job

- **Project-only navigation:** simpler payload, but insufficient for this existing job. It drops the selected proposal and may leave the user in History or an unrelated editor, requiring them to find the concern again. It is not an equivalent substitute.
- **Keep the current one-shot handoff:** preserves known behavior with low immediate change. Its map/event and destination effect remain additional coordination alongside the shell opener registry. Their existence alone is not proof they must all be replaced.
- **Candidate explicit navigation intent:** carry project ID, target proposal ID and a distinct request identity through the proposed Desk navigation boundary. Let the Room own the reveal transition and its drafts; keep the intent transient/consumed rather than making it durable domain state. This could remove duplicated coordination only if it actually replaces an existing handoff mechanism, not adds another queue. It must retain repeat-target reveal and avoid autosave, auto-confirm or reissuing a send. Exact implementation remains unapproved.

**Decision and limits:** retain target-level context, not just destination-level context, when consolidating director oversight with project work. Before replacing the handoff, prove warm and newly mounted Room behavior, a repeated target, pending/failed Save with newer edits, and an already-settled or unavailable proposal. The inspected reveal waits when no target row exists; a truthful settled/unavailable outcome remains a validation question, not proof of a reproduced stuck view. None of this requires merging oversight, proposal, update or send authority, or adding a new workspace.
