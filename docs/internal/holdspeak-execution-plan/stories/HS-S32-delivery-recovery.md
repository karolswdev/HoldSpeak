# HS-S32 · Continue a known delivery without recreating its PR

**Conditional design, not implementation authority.** Epic: [HS-E30](../epics/HS-E30-recovery-outcomes.md). D21/G32 remains pending. Source pin: `80b641fa41c7352280cfa52e933acf6dbe8d3857`. No application or test was executed while authoring.

## Outcome and explicit scope

After a Program is Done, delivery can need attention without reopening or rerunning its work. The owner should distinguish a failed local preparation, a known delivery PR and an uncertain remote result, then continue the same delivery only when identity and authority are established.

This first branch covers **known-PR continuation and stage-aware handled failures**. It does not solve process death, escaping exceptions or post-effect ledger-write failure during initial automatic delivery or full preparation Retry, add a general durable dispatch claim, or promise exactly-once delivery. That broader crash/restart contract remains separate: current `_write` can perform remote effects before any delivery line exists, and `_deliver_once` can later see no line after an escaping exception. Do not describe the existing suppression as universal. Catching ordinary exceptions does not close that crash window.

The [source trace](../NEXTGEN-JOURNEYS-AND-NAVIGATION.md#delivery-recovery-appendix-a-retained-pr-is-not-reused-by-retry-1000-follow-up) establishes a concrete orchestration mismatch, not a reproduced duplicate PR: a failed merge retains PR number/branch, but Retry runs the full worktree/DW/commit/push/create path. Successful known-PR continuation must not run those preparation commands again. Program Done, delivery result and historical receipts remain different facts.

## G32 choices and proposed first branch

Resolve these local choices before implementation; no answer is inferred by writing tasks:

1. **Known outcome first.** Proposed: an explicit read-only Check action reconciles a sufficiently identified PR. A matching open PR with no unresolved merge-attempt marker can then offer an explicit owner Merge; a matching already-merged PR records reconciliation as delivered without another merge. Closed-unmerged, ambiguous, unavailable or identity-mismatched results do not recreate, reopen, force-push or merge anything. After any unconfirmed merge attempt, retain a merge-requested/uncertain marker: open/queued observations and later Check do not reoffer Merge. Clearing it needs a separately defined proof/resolution, outside this first branch. Some failed initial Normal/YOLO merges will therefore remain Check/Skip until externally resolved; this conservative restriction needs G32 acceptance. Proposed for G32: Skip ends local delivery follow-up and leaves Program Done; it does not establish the remote result. Preserve “Done, not delivered” where recorded no-effect evidence supports it, but queued/unconfirmed effects must retain their uncertainty rather than inherit that unconditional wording.
2. **Recovery is not a new automatic policy.** Initial Secure/Normal/YOLO delivery behavior remains. This proposed recovery branch requires a fresh explicit owner action for merge after Check, only when no unresolved merge-request marker remains. A fresh initial Secure PR retains its direct owner Merge entry, but that press still performs the accepted binding/read/head-guard/result-confirmation protocol; it does not require a separate prior Check. If the owner instead wants policy-driven automatic continuation, that is a separate accepted rule and proof scope, not a hidden consequence of a read.
3. **Truthful handled stages.** Proposed optional receipt metadata records the attempted stage, whether a remote write was attempted, and acknowledged identity. Preparation Retry is offered only when recorded evidence establishes failure before any remote push/create/merge attempt and no prior delivery receipt for the Program establishes a conflicting remote effect. A nonzero response, parse failure or thrown transport exception after a remote attempt is uncertain, not safe-to-repeat.
4. **Legacy identity is incomplete.** Existing lines have PR number/branch but no original repository/head/base receipt. A title-derived branch is not unique to a Program. Do not adopt a PR by branch/title, infer original authority from a currently reassociated repository, or equate no search result with no effect. Legacy/incomplete and uncertain-create cases remain explained/blocked with Skip available; a wider manual identity-confirmation or discovery flow is not part of this first branch. This compatibility restriction needs explicit acceptance.
5. **New receipts preserve enough identity.** Proposed additive metadata retains the acknowledged canonical PR URL/number, intended branch/base and prepared head commit, delivery target and phase evidence. Preserve old `undo.pr_number`/`undo.branch` fields for current readers. Exact metadata names/version are proposed, not existing APIs. Compare the read response against the recorded identity; changed head/base or another repository requires a decision rather than automatic adoption.
6. **Bind the displayed action.** Proposed additive `expected_delivery_checkpoint_id` names the actual ledger row shown to the owner, not a freshly inferred current row. Carry it through the Program UI/API and supported adapters; validate it under the existing service decision lock before Check/Retry/Merge/Skip, each of which may write history or effects. Freeze it in briefing-page content. A legacy page/client without the required binding must refuse the recovery write and ask for fresh context, never silently use the latest receipt. Non-delivery decisions remain unchanged. Exact field names are proposed.
7. **One bounded request receipt, not a general lifecycle.** For every owner-initiated known-PR Merge, including a fresh Secure PR, first append and successfully commit a `kind="delivery", choice="pr_open"` checkpoint containing the immutable identity and owner-requested/unconfirmed marker. Only then issue the remote command. This says the owner requested a merge, not that it ran, is active or failed. It projects Check/Skip and remains so after interruption, even if the command never started. Preserve it on every subsequent observation/error row until confirmed merged. This explicitly proposed G32 barrier protects that narrow request path; it is not a durable cross-process lock and does not close the initial automatic/preparation-Retry windows. Do not add a general started/in-progress state or infer missing markers for old history.

A smaller accepted subset may improve known-PR handling while leaving additional states blocked; report exactly which cases are implemented. If legacy automatic recovery or crash-safe dispatch is required for acceptance, stop this branch and expand the local contract before code changes.

## Ownership and preservation

The existing delivery module remains the orchestrator; the existing Program checkpoint ledger remains history. The Program service remains the owner-only decision admission boundary. No separate workflow engine, scheduler, global operation registry, new table or mandatory source-registration dependency is proposed.

A Program may be created from a repository path and has no required registered `source_id`. Existing PR-receipt service methods are useful precedents but cannot simply be wired in as though every Program has their required source. Any new read adapter is delivery-local through the existing injected runner command boundary, using the recorded repository context, bounded output and ordinary failure handling. Check is read-only toward the provider; it may append a truthful local observation receipt. A read result is evidence, never a grant to merge. For the accepted recovery path, use the recorded canonical PR target and a provider-supported conditional-head merge, then observe the result. The official CLI documents `--match-head-commit`, but installed support must be verified under assignment. This atomically guards the head only; base/fork checks remain read-time facts, not a full remote transaction. A queued/open result is not Delivered merely because the merge command exited successfully. No `--admin`, forced merge, automatic repeat or branch deletion is added; Skip does not cancel a provider-side queued merge. See V32 for the checked command documentation.

Preserve the existing final Done evidence allowlist. Do not expose transcripts, briefs, worktree paths, raw provider stderr or private source material in the recovery row/PR. Preserve phase-close evidence without rerunning Delivery Workbench; current merge failure can drop that metadata, so retain the original phase facts through failure/check/recovery rather than asserting a phase closed from a friendly string.

A closed Program can still receive a new delivery target through the current update path without changing its last delivery-row ID. Known-PR continuation must use the recorded original target/phase in both words and effects; a changed current target cannot silently retarget an old PR. Preparation Retry refuses current-versus-recorded target drift pending a separate decision. Re-read relevant Program state under the decision lock.

Do not rewrite ledger history. New outcome/reconciliation rows retain their relationship to the identity being checked. A current read does not erase the earlier failure; Skip does not assert that a remote PR vanished. For the proposed uncertain-result Skip branch, keep the prior acknowledged identity and unresolved observation visible after the held row is removed. G32 must review the receipt/projection and settled-brief representation that supports this; no new schema or storage format is selected here. Skip itself performs no provider read or mutation and starts no automatic recheck. A local terminal skipped receipt is neither confirmed delivery nor proof that queued work stopped. No generic exception may silently become delivered.

## Rollback and stops

Use a reviewed reverse patch for the accepted branch, preserving the appended history and old optional-field readers. Reverting recovery code cannot remove a pushed branch/PR, undo a merge or safely reissue an uncertain operation. A rollback that restores broad Retry restores the earlier limitation; disclose it. No DB purge, history rewrite, force push or owner-worktree cleanup is a rollback step. Old code interprets `pr_open` as Merge and ignores the new marker: readable history is not safe downgrade execution. If unconfirmed request markers exist, do not resume an unguarded older version; retain a reviewed compatibility refusal or hold the downgrade until resolved. A plain reverse patch is insufficient in that state.

Stop for unresolved G32/legacy behavior, insufficient repository/PR identity, an unproven remote outcome, new durable in-progress/restart requirements, unsafe real-remote tests, widened authority or an assumption that a numeric PR is globally unique. Preserve [I10/I16/I18/I21/I24](../INVARIANTS.md).
