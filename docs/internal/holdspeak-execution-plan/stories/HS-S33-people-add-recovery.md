# HS-S33 · Recover a partially saved People promise

**Detailed conditional proposal; implementation not assigned.** Epic: [HS-E30](../epics/HS-E30-recovery-outcomes.md). G-ADD, locally **G33**, remains pending in [Decisions](../DECISIONS.md). Source pin: `80b641fa41c7352280cfa52e933acf6dbe8d3857`. This connects a leader's intended promise to its existing encrypted request/commitment identity. It does not introduce a common recovery service.

## Job and source truth

When the owner presses Add under “I owe”, the product creates a request and then accepts that request. If the second operation fails or its response is lost, the owner should continue the acknowledged request rather than unknowingly create another promise. A successful response must identify what was saved; newer drafting must remain intact.

`PrepPane.addOwe` in `web/src/pages/cores/PeopleCore.tsx` currently holds the returned request ID only inside the two-await callback. Generic failure copy says “Nothing changed”, and another Add starts with a fresh request. `EncryptedPeopleStore.create` creates a fresh UUID each time; matching words are not a deduplication key. In contrast, `EncryptedPeopleStore.accept_request` already atomically links a request and commitment and returns the same commitment when that same accepted request is replayed. Preserve this existing useful behavior.

The public request omits the internal `accepted_commitment_id`. Reconciliation must join exact commitment `request_id` plus relationship ID, not the nullable `commitment_id`, text, time or source. The HTTP surface has no GET-request endpoint; read the existing relationship detail. That detail is assembled from separate reads, so contradictory states require reread rather than an assumed atomic snapshot. Its arrays include terminal commitments: Done or dismissed is not permission to reopen/recreate.

Create can persist before a later private-file/readback failure returns 503. Acceptance can commit before transport/response loss. A status code alone does not establish rollback. A known create refusal is narrowly provable only through the exact pre-write error contract; a generic 503, malformed success or lost response has an unknown result.

Evidence: [two-write journey](../NEXTGEN-JOURNEYS-AND-NAVIGATION.md#director-commitment-recovery-one-add-spans-two-durable-writes-1530-follow-up). Exact current paths, proof ownership and proposed commands: [V33](../VALIDATION.md#v33-people-add-recovery-verification). These are source findings, not a reproduced user incident.

## G33 choices and limits

- **A, retained-request recovery, specified here:** add a small component-local attempt receipt and explicit read/check/accept controls within existing `PeopleCore.tsx`. Reuse existing endpoints, store idempotency and ordinary People views. No new production file, schema, endpoint or durable receipt store.
- **B, atomic create-and-accept command:** separately design a domain operation and caller-supplied operation identity if crash/reload/cross-window creation deduplication is required. Merely combining two calls server-side is not enough to resolve a lost creation response. Choosing B stops A's implementation brief for revised design.

A is deliberately **same-mount recovery**, not crash/reload/cross-window exactly-once creation. Its receipt and submitted private context remain in memory; full unmount/reload loses them. Existing ordinary Desk drafts already persist in workspace storage, and this slice neither silently fixes nor expands that custody. Do not put new receipts, private IDs or submitted copies in drafts, places, localStorage or a general operation registry. Existing requests/commitments can still be inspected manually after remount; matching their words cannot recover an unknown attempt identity.

G33 must accept these local semantics before implementation:

1. Capture the intended relationship, exact submitted words/visibility, acknowledged request ID when present and attempt generation. Use an independent synchronous in-flight guard; unrelated Prep actions cannot release it by overwriting the generic `busy` string. Rapid Enter/clicks cannot duplicate the same local attempt.
2. After a valid create acknowledgement, continue acceptance only while that same attempt/person remains mounted and intended. Back, close or actual person change detach the continuation. Fold/lens changes do not detach the still-mounted Prep. Already issued writes may still commit; detaching is not cancellation or rollback.
3. If acceptance lacks valid acknowledgement, keep the known request identity and truthful partial/uncertain copy. **Check saved request** is a read only. A matching requested record enables a separate explicit **Accept saved request** action; no read automatically accepts. Show the original submitted words so a newer draft is not mistaken for the saved request.
4. A complete current relationship read showing the exact accepted request and exactly one matching commitment confirms the saved promise, including terminal commitment states. Show the actual saved commitment words/state: another explicit acceptance may legitimately have supplied a body override. Do not require commitment text equality or overwrite it. Before offering acceptance of a still-requested record, require its words/visibility to match the held submission; otherwise stop for inspection. Missing arrays, wrong relationship, absent request, inconsistent accepted/requested state or multiple matching commitments stay unresolved. A requested record plus a newly linked commitment can be an ordinary between-list read race, not proven corruption; reread without another effect. Never infer no effect from absence or resurrect a terminal item. Retrying a known ID may refuse after archive; preserve that refusal rather than invent a new request.
5. With no usable acknowledged ID, do not call fresh creation “Retry”. Keep the draft and explain that creation could have happened; offer existing People inspection. Only after the current request has settled, a separate **Start another promise** requires an explicit local acknowledgement that it creates a new request and may duplicate the earlier one. It performs no write until the owner intentionally presses Add. Known precise pre-write refusals may return to ordinary editing without this uncertainty warning; enumerate the codes, never classify by HTTP status alone.
6. Completion may clear only the exact unchanged submitted draft for the same live attempt/person. Use both current raw text equality and conservative change evidence, not equality alone. Any newer draft, including away-and-back edits, is preserved. If the guard cannot prove unchanged intent, leave the text and identify the saved result; do not automatically clear or close it.
7. Explicit owner-auth/protected-key failures hide/clear new protected receipt context and the People view. A generic store 503 does not distinguish lost key from outage: perform a guarded read-only `/api/people/readiness` check. A current `ready` answer permits retaining the ordinary-outage view; a non-ready answer clears protected view/receipt and invalidates continuation. If readiness is itself failed/malformed, conservatively clear/hide them, suspend recovery writes and explain without private detail that a save may exist. That protective fallback loses the in-memory binding and requires later manual inspection; existing ordinary drafts are not erased. Reopening/ready alone never accepts or creates. G33 must accept this explicit uncertainty tradeoff. Generic “Nothing changed” cannot overwrite a known/possible write, and late callbacks cannot resurrect cleared context.
8. Accept the bounded person-host identity guard described below and its reset of ephemeral pane state on actual person change. Persisted per-person drafts/lens choices remain; no broad cache or read-lifecycle migration is included.

No automatic external Send, alias resolution, report-owes creation, agenda action, commitment Done, Nudge copying or privacy-policy change belongs to this slice.

## Narrow implementation design

One existing production owner: `web/src/pages/cores/PeopleCore.tsx`.

- Keep a cohesive local discriminated attempt state/ref in Prep, with exact names proposed: initial, creating, request known, acceptance uncertain, saved, creation uncertain. Network-pending state and known outcome must be distinct. Validate nonempty IDs, matching relationship/request linkage and payload shape before acknowledgement; `apiFetch` can return `{}` on malformed successful JSON.
- Use the existing complete GET relationship read for explicit reconciliation, checking actual arrays and exact IDs. Do not reconcile from a roster fallback row or merely optional arrays on the current prop. Older checks cannot overwrite newer receipt truth. Existing “Asked of you” acceptance of the held request must use the same guard/receipt handling, or be visibly disabled while that attempt is pending; unrelated request acceptance retains its current semantics.
- Bind the pane to the intended host relationship, not whichever late detail response lands. In the roster `select`, person-window `read`, and their render boundaries, invalidate stale read generations on person change, Back/unmount and protection clearing; guard success, failure and loading settlement, and reject detail whose ID differs from the requested host. Key the relationship pane by the intended person if needed to reset per-person ephemeral attempt state. Preserve the mounted pane and its receipt throughout a same-person refresh, including while fetching and on ordinary refresh failure; do not temporarily clear/key-change/unmount it as the current roster select can do. Preserve the existing visible-state-on-outage behavior. This is bounded identity safety, not adoption of a new query framework.
- Track local draft edit generation and capture the current immutable Desk `drafts` map reference at submit. `compositorSlice.setDraft` replaces that map for every real write but no-ops an identical value. Together with same attempt/person and raw text equality, unchanged map identity is a conservative clear gate, including another window's away-and-back edits. An unrelated draft write may leave submitted text behind; that is acceptable rather than losing newer intent. Do not modify the shared store to add a global revision system.
- Handle Add failures locally with outcome-aware text. Invoke the existing protection-clearing behavior with a scoped context or equivalent local branch so it does not overwrite that truth. Explicitly cover 401/403, which the current protected-failure helper does not classify. Since `_require_ready_owner` maps missing/locked/corrupt-key readiness to the same public store-unavailable 503 as other failures, use the existing readiness endpoint for the scoped distinction, with the accepted protective fallback when that read is uncertain. Guard its success/failure by host and attempt; a current ready observation is not a perpetual guarantee. Do not expose private content in error logs, screenshots or persistent receipts.
- On acknowledgement/reconciliation, refresh existing People data without new polling/subscriptions. A refresh failure cannot retract a valid acknowledgement or claim nothing happened. Local “saved” does not mean current commitment remains open.

## Rollback and stops

Reverse only the assigned UI/test/capture diff. There is no schema or durable receipt migration. Reverting restores the current two-call limitation; it cannot erase requests/commitments already saved, reopen terminal work or prove an uncertain write did not happen. Do not delete suspected duplicates as rollback.

Stop for unresolved G33, source drift, required durable/cross-window guarantee, new endpoint/store/privacy scope, undefined protection clearing, unsupported complete-read shape, unsafe key/provider fixtures, undeclared production paths or failed identity/draft/geometry proof. A test failure is not permission to loosen admission or call text matching idempotency. Shipping and repository implementation remain separately assigned actions.
