# Research Brief for the Ultimate HoldSpeak “Workbench 2.0 on Steroids” Design + SRS Specification

## Executive summary

The most important research finding is that this is **not a greenfield Amiga-inspired redesign**. HoldSpeak has already crossed that bridge.

The current repository explicitly records the owner’s requirement that the Desk OS should feel like “Workbench 2.0 on steroids,” and Phase 105 was chartered specifically from that direction. That phase shipped a Workbench-derived icon system, drawers as real windows, Info on objects, contract-driven drop behavior, a registry-driven menu bar, persistence rules, and a written Desk grammar. Its own final summary identifies the remaining specification debt rather than treating the concept as aspirational. fileciteturn27file0L2-L2

The correct mission for a developer/specification agent is therefore:

> **Formalize, reconcile, complete, and harden the existing HoldSpeak Desk OS into an authoritative design specification and SRS, rather than inventing a replacement UI.**

That distinction changes nearly every architectural recommendation.

HoldSpeak Web is already a typed React/Vite application whose canonical operating surface is the Desk. The current architecture has only three rendered routes—Desk, arrival, and Presence—while other product destinations become windows on the Desk. The spatial world is a Pixi/WebGL scene backed by Zustand; ordinary application windows are DOM-composited above it; HTTP goes through a typed client; and one runtime WebSocket bus serves the React tree. fileciteturn18file0L2-L2 The current dependency set already includes React 19, React Router, TanStack Query, Zustand, Motion, `@use-gesture/react`, PixiJS, Three.js, CodeMirror, xterm, Vite, Vitest, Testing Library, axe-core, and Puppeteer. fileciteturn11file0L2-L2

The existing design discipline is unusually mature. HoldSpeak already has:

| Existing asset | Status and significance |
|---|---|
| `docs/internal/CONSTITUTION.md` | Governing product doctrine; other UI documents defer to it. |
| `docs/internal/AGENT_BRIEF.md` | Required UI-development method and current OS-level ambition. |
| `docs/internal/DESIGN_SYSTEM.md` | Token architecture, component states, window physics, material, motion, accessibility. |
| `docs/internal/UX-CANON.md` | Face-level laws: library controls, no generic prose, no modal editing, honest states, owner-gated screenshots. |
| `docs/internal/DESK_GRAMMAR.md` | Explicit “Workbench 2.0 on steroids” world-layer laws. |
| `web/ICON-DISCIPLINE.md` | Pixel-art geometry, state-image rules, badges, system sprite grammar. |
| `web/src/desk/surface/contract.md` | Component APIs, states, ARIA behavior, motion and responsive composition. |
| `web/design-tokens.json` | Design-system source of truth, generated into CSS and TypeScript. |
| `web/src/desk/components/DeskWindow.tsx` | One window shell and physics implementation. |
| `web/src/desk/store/*` | Spatial/window/application lifecycle and persistence state. |
| `web/public/desk/sprites/` | Existing Workbench-inspired object art with explicit selected/stale states. |

The repository’s own standing agent brief says that the world layer already “speaks the Workbench grammar,” identifies `DESK_GRAMMAR.md` and `ICON-DISCIPLINE.md` as law, and directs future work toward native-feeling interiors, direct manipulation, meaningful motion, global keyboard grammar, universal context menus, cross-boundary drag-and-drop, a system shade, and Files-grade object browsing. fileciteturn30file0L2-L2

The historical Amiga research strongly validates the direction HoldSpeak has already taken. Commodore’s 1991 *Amiga User Interface Style Guide* treats metaphor, object-before-action interaction, visible focus, immediate feedback, subdued/non-color-only signaling, user preferences, adaptable fonts, localization, physical-looking controls, drag operations, context-sensitive menus, window persistence, and multiple interoperable interface modes as core principles. citeturn9search1turn12view0turn12view1 Those are much more useful than copying a beige/grey palette or reproducing old bitmaps.

The final specification should consequently pursue **Workbench behavior and Intuition philosophy rather than retro cosplay**:

- Objects should look and behave like objects.
- Selection must visibly change the object.
- Actions should apply to the current object or selected group.
- Windows should remember the user's arrangement.
- Menus should disclose the available command vocabulary.
- Disabled capability should be honest and comprehensible.
- Direct manipulation should coexist with complete keyboard/pointer alternatives.
- Small-scale clarity, restrained depth, and immediate feedback matter more than nostalgia.
- Voice, keyboard, graphical interaction, automation/MCP, and desktop integration should all be alternate entrances to the **same product capabilities**, echoing the Amiga’s GUI/Shell/ARexx philosophy rather than creating independent state models. Commodore explicitly treated GUI, Shell, and ARexx/IPC as complementary interfaces and recommended supporting all three. citeturn11view0

The strongest technical recommendation is likewise conservative: **retain React/Vite, the existing HoldSpeak design system, Pixi spatial world, Zustand Desk state, FastAPI integration, and registry-driven interaction grammar.** A desktop container should be specified as a thin host boundary, not as a second application architecture. Tauri and Electron deserve an ADR and prototype, but neither should own product state or visual components. Tauri uses an OS WebView with Rust/message-passing and a capability/permission model; Electron bundles Chromium and Node.js, producing a consistent rendering target but demanding careful context isolation, sandboxing, navigation restrictions, and IPC validation. citeturn8search8turn6search6turn8search0turn6search0

Finally, accessibility cannot be treated as a “modern compromise” that weakens the Amiga metaphor. It actually strengthens it. WCAG 2.2 AA now explicitly requires a non-drag pointer alternative for functionality implemented through dragging, introduces minimum pointer-target constraints, and requires keyboard focus not to become obscured by authored content. citeturn7search0turn7search8turn7search9 These requirements map naturally to Workbench’s original commitment to multiple ways of acting on an object.

## Repository reality and architectural constraints

### The product architecture that the specification must preserve

HoldSpeak describes itself as a Desk connecting voice typing, meetings, project records, and AI work. The Desk has an arrival surface, a Floor of records represented as objects, and application/tool windows such as Speak, Meetings, Settings, Threads, and project-related work. fileciteturn10file0L2-L2

At the frontend level, the repository is already architected as an operating surface rather than a conventional route-centric web application:

```mermaid
flowchart TB
    Hub["HoldSpeak WebRuntime / FastAPI"]
    HTTP["Typed HTTP API"]
    WS["Single RuntimeBus /ws"]
    React["React 19 Desk application"]
    Store["Zustand Desk store"]
    GL["Pixi/WebGL world"]
    Windows["DOM Desk windows"]
    Surface["Surface component library"]
    Tokens["design-tokens.json"]
    Objects["Desk objects / drawers"]
    Desktop["Future desktop host boundary"]

    Hub --> HTTP
    Hub --> WS
    HTTP --> React
    WS --> React
    React --> Store
    Store --> GL
    Store --> Windows
    Surface --> Windows
    Tokens --> Surface
    Tokens --> GL
    GL --> Objects
    Desktop -. "bounded host services only" .-> React
```

This is not merely a conceptual target. The canonical frontend architecture says the world layer is a Pixi v8 scene graph fed by the Desk store, windows are DOM-composited above it, `src/lib/api.ts` is the HTTP boundary, and `RuntimeBus.tsx` is the product WebSocket owner. It also mechanically guards the rule that product surfaces belong in Desk windows rather than becoming independent route-worlds. fileciteturn18file0L2-L2

The HTTP abstraction is already narrow and useful: `apiRequest`, `apiFetch`, and `apiBlob` automatically pass authentication, standardize JSON handling, and surface an `ApiError` carrying status and backend payload. fileciteturn24file0L2-L2 The architecture document additionally states that provider credentials must not enter Web state or storage and that the runtime bus is shared rather than recreated per feature. fileciteturn18file0L2-L2

The final specification should therefore define **interfaces around these boundaries**, not create new fetch clients, feature-local sockets, or desktop-specific duplicates.

### Windowing is already a first-class subsystem

`DeskWindowFrame` is explicitly documented as **the one window contract**. Its private physics layer already owns dragging by the title bar, resize, focus-to-front, remembered geometry, minimize/maximize/close state, clamping, snapping, compact bottom-sheet behavior, fit-content growth, origin-aware open/close motion, and reduced-motion handling. fileciteturn16file0L2-L2

The Desk state model exposes the corresponding domain vocabulary. It includes:

- `PanelRect {x,y,w,h}`
- `WindowInstance`
- spatial/list `DeskView`
- per-zone view/sort preferences
- pullout, drawer, repository, roadmap and Workbench windows
- selected IDs
- drag/hover state
- persisted panel rectangles
- saved geometry
- panel order
- minimized/maximized sets
- normalized application windows
- application-opening and object-opening commands

and a very large set of product actions that mutate backend-backed primitives rather than merely altering presentation. fileciteturn23file0L2-L2

That makes a critical SRS distinction possible:

> **Visual window state is not application/business state.**

The specification should formalize the current separation among:

1. **Backend truth** — Notes, Meetings, Threads, Workbenches, Projects, receipts, model state, etc.
2. **Workspace state** — open windows, rects, stacking, list/spatial preferences.
3. **Ephemeral interaction state** — hover, drag candidate, focused object, open menu.
4. **Host state** — future native tray, platform shortcuts, system notifications, file-dialog permissions.
5. **Rendering state** — animation progress and GL/DOM presentation details, which must never become the authoritative record.

### The Workbench concept is already implemented

Phase 105 is perhaps the single most important repository source for this research. Its charter was exactly the user’s proposed vision. It shipped, among other things:

- 64×64 pixel-art object sprites rendered 1:1.
- Real rest/selected/stale image variants.
- Deterministic grid placement.
- Drawer windows with icon/list modes.
- Persistent drawer view/sort/open state.
- An Info contract for every object kind.
- A data-driven drop matrix.
- A unified verb registry.
- Menus built from that registry.
- A written Desk grammar.
- Mechanical guards for these laws. fileciteturn27file0L2-L2

`DESK_GRAMMAR.md` then turns these decisions into law. It says, for example, that default icon homes are deterministic while user placement is sacred; mouse single-click selects and double-click opens; windows coexist; zones are drawers; valid drops are declared by contract data rather than hardcoded by individual components; menus ghost unavailable operations with explanations; and menu bar, context menus, window-head menus and dock menus all derive from one verb vocabulary. fileciteturn28file0L2-L2

The icon discipline is similarly explicit: each object uses a uniform cell, importance is expressed through state rather than arbitrary scaling, silhouettes must be distinct, selected/stale states are real generated assets, decorative badges are forbidden, and state badges may appear only when a named live field supplies the fact. fileciteturn29file0L2-L2

The repository also contains the actual sprite family under `web/public/desk/sprites/`, including base, `_sel`, and `_stale` assets, so the specification agent should treat the current art directory as empirical source material, not merely prose documentation. fileciteturn32file0L2-L2

### Existing design-system and accessibility infrastructure

HoldSpeak’s surface library already defines a closed state vocabulary:

`idle · active · working · success · warning · failure · unreachable`

and requires states to be conveyed using icon plus text rather than color alone. Its component contract specifies roving tab stops for composites, ARIA-expanded disclosures, focus behavior for popovers, `aria-live` transitions, real radio inputs, tokenized motion, reduced-motion support, and container-based responsive layout. fileciteturn14file0L2-L2

The UX Canon is even stricter. Its current laws include:

- every verb uses the component library;
- substantial UI is mocked before implementation;
- generic explanatory prose is generally a defect;
- editing happens in-world rather than in modal workflows;
- names are not redundantly repeated;
- zero-valued counters are omitted when they convey nothing;
- network egress is indicated at the point at which egress occurs;
- states and failure reasons must be honest;
- dead verbs do not ship;
- setup must be self-evident;
- screenshots are part of the acceptance procedure;
- scrolling and compact layout behavior are standardized. fileciteturn13file0L2-L2

The current CI is unusually compatible with converting a design specification into executable law. `npm run check` already combines token-generation checks, token validation, architecture guards, strict TypeScript, frontend tests, the production build, and a bundle gate. The repository’s primary GitHub Actions workflow additionally runs documentation validation, critical journeys, unit tests with coverage, macOS integration tests, browser E2E tests, a required live runtime-bus test, Mermaid rendering validation, and Linux smoke coverage. fileciteturn11file0L2-L2 fileciteturn21file0L2-L2

This leads to a core instruction for the final specification agent:

> **Every normative UI rule that can be mechanically verified should name the guard that proves it.**

### What remains genuinely unfinished

The repository itself names several relevant debts.

Phase 105 identifies behaviors that still existed only as TypeScript implementation rather than a portable written contract: drag thresholds and mechanics, clean-grid layout math, bob animation envelope, drawer-window fly-out motion, menu dismissal behavior, and Info-card composition order. It also lists cross-window re-filing, multi-object drops, object receipts, richer drawer arrangement and additional desktop/workspace behaviors as follow-up work. fileciteturn27file0L2-L2

The current Desk grammar still records standing remainders including drawer rearrangement, cross-window drag refiling, the record orb as a drop target, multi-object drops, per-object receipts, and an artifact sprite that does not yet read well at its intended scale. fileciteturn28file0L2-L2

There is also measurable design-system debt. The UX Canon’s ratchet records raw `<button>` violations as a dated down-only count of 175 on September 17, 2026, while maintaining hard-zero requirements for certain other rules. That does not invalidate the design system, but it means “all verbs use the library” remains a target invariant with known legacy residues. fileciteturn13file0L2-L2

The design system also records a deliberate “dark-only” decision while noting that the semantic token layer is the attach point for a future light theme. fileciteturn19file5L70-L82 This is especially relevant because the requested SRS explicitly needs a theming requirement rather than merely a skin description.

Finally, desktop wrapping is not current HoldSpeak doctrine. Earlier investigations explicitly chose the Web Desk as the specification and declined adding a Tauri shell or second UI kit in those scopes. fileciteturn34file0L2-L2 An earlier study likewise rejected an Electron shell as unnecessary scope for its problem. fileciteturn31file0L1-L10 Because the present assignment explicitly assumes web **and** a future Electron-or-Tauri desktop target, this is a **new architectural constraint that requires an ADR**, not something an agent should silently infer from the repository.

## Amiga Workbench and Intuition principles to preserve, modernize, and reject

### What “Workbench-inspired” should mean

The original Amiga GUI was conceptually split between **Intuition**, the GUI system/tooling, and **Workbench**, the default graphical environment. Commodore’s style guide describes the combination as a system in which familiar metaphors, consistent interaction rules, and standard UI elements reduce the amount users must memorize. citeturn12view0

That makes “Intuition-inspired Workbench 2.0+” a useful architectural concept rather than a visual theme:

**Intuition inspiration** should govern the component and interaction system.

**Workbench inspiration** should govern the desktop metaphor, object organization, windows, menus, drawers, selection and direct manipulation.

**HoldSpeak** should supply the modern capabilities—voice, models, streaming, receipts, project context, synchronized data and automation.

### Principle crosswalk

| Amiga principle | Primary-source basis | HoldSpeak adoption | Required modernization |
|---|---|---|---|
| **Familiar physical metaphor** | Commodore says GUIs can expose complex systems as familiar objects and activities. citeturn12view0 | Desk objects, drawers, windows, Info, filing. | Do not force metaphor where it makes an AI/workflow task less clear. |
| **Object → action** | User selects the thing first, then the action; this reduces modal interaction. citeturn12view0 | Selection + registry verbs + context menu. | Also expose keyboard and touch equivalents. |
| **Avoid modes** | Original guide explicitly warns about confusing modes. citeturn12view0 | No modal edit workflows; in-place edits. | Explicit temporary states must remain visibly announced and escapable. |
| **Visible focus** | Focus is described as a useful information channel. citeturn12view0 | Active window, selected object, focus ring. | WCAG focus-visible and focus-not-obscured become normative. citeturn7search0turn7search9 |
| **Immediate feedback** | Every action should show an immediate reaction. citeturn12view0 | Selected sprite states, pressed controls, drag target lighting, progress. | Response must work with keyboard, screen readers and reduced motion too. |
| **Raised/recessed geometry** | Release 2 introduced an upper-left-light 3D grammar; interactive controls visibly depress. citeturn12view0 | HoldSpeak bevel, etch and pressed-state tokens. | Keep subtle enough for long-duration work; do not reproduce low-resolution bevels literally. |
| **Color is supplemental** | Commodore explicitly says not to use color as the sole cue. citeturn12view0 | `StateChip` icon + text; selected cell has multiple cues. | WCAG contrast and forced/high-contrast modes must also be tested. |
| **Unavailable controls are clearly unavailable** | Original gadgets were ghosted, and selecting something that does nothing was discouraged. citeturn12view0turn9search7 | Menus ghost with a reason; dead body verbs are generally omitted. | Preserve that **jurisdiction distinction**: menus teach capabilities by ghosting; ordinary content should not accumulate useless controls. |
| **One current selection context** | Commodore recommends one current object/group and one selection level at a time. citeturn12view0 | Desk `selectedIds`, current object context. | Define nested-selection boundaries explicitly for content inside windows. |
| **Windows establish context** | Everything inside a window should share a meaningful bond. citeturn12view1 | Application and object windows. | Never use windows as arbitrary cards; every window gets identity, job and state lifetime. |
| **Safe window activation** | Title bar is suggested as a click target that activates without altering content. citeturn12view1 | `DeskWindowFrame` head and focus-to-front. | First click on an inactive content window must not accidentally execute a destructive/material action. |
| **Remember user geometry** | Commodore recommends remembering user-chosen position and size, temporarily and optionally persistently. citeturn12view1 | HoldSpeak already persists rect/order/max state. | Version the workspace schema and support viewport migration. |
| **Zoom as reversible window state** | Original zoom toggles between alternate and previous geometry. citeturn12view1 | maximize/restore. | Support snapping, expose/switcher and compact layouts without losing original geometry. |
| **Context-sensitive menus** | Active-window context determines available menu actions. citeturn9search2 | One verb registry and menu adapters. | Menus must also work through keyboard, context-menu key and touch equivalents. |
| **Menus as discoverability** | Menus let users browse capabilities while keeping the normal surface uncluttered. citeturn13view1 | Desk/Object/Go/Window menus; ⌘K shelf. | Registry should generate shortcut sheet and command palette as well. |
| **Icons communicate quickly** | Workbench icons are functional handles and visually change on selection. citeturn9search0turn9search4 | Real sprite state sets and consistent cells. | Original art must remain inspiration; HoldSpeak’s own coherent sprite family remains canonical. |
| **AppWindows accept drops** | Workbench defined explicit areas into which objects could be dropped. citeturn12view1 | `dropMatrix.ts` declares target capabilities. | Every drag function also needs a non-drag pointer mechanism under WCAG 2.2. citeturn7search8 |
| **Progress should remain usable** | Original guidance favors visible progress for measurable work with a stop action. citeturn12view0 | `ProgressPlan`, working states, receipts. | Support cancellation only where cancellation is truthful; never fabricate progress. |
| **Respect user visual preferences** | Amiga applications were expected to honor user fonts, resolution and palettes. citeturn12view0turn13view2 | Semantic token system, reduced motion, container layout. | Add formal theme, contrast, text scaling and motion preference contracts. |
| **Design for constrained environments** | Commodore recommended validating at a least-common-denominator 640×200/Topaz-8 configuration. citeturn12view0 | HoldSpeak already tests compact 393-width compositions. | Adopt the principle, not the literal resolution: test every surface at defined minimum containers and large text. |
| **Internationalization from the start** | Commodore warns translated text can grow roughly 30–50% and recommends centralizing strings. citeturn12view0 | Not yet a strong visible part of the Desk contract. | Externalize user copy, stress-test expansion/Bidi, and format locale-sensitive data through a common service. |
| **Multiple interfaces to one capability** | Amiga encouraged GUI, Shell and ARexx/IPC interfaces to coexist. citeturn11view0 | GUI, voice, API, MCP and automation already coexist in HoldSpeak. fileciteturn10file0L2-L2 | Define commands once, expose them through multiple adapters, and never fork policy or business semantics. |

### Principles not to reproduce literally

The final specification should explicitly reject several historical implementation details while preserving their intent.

**Do not reproduce fixed low-resolution layouts.** The useful principle is “works at the least capable supported presentation,” not “pretend the display is 640×200.” Commodore itself framed that resolution as a compatibility test rather than a required default. citeturn12view0

**Do not make double-click the only activation mechanism.** Workbench traditionally used single click for selection and double-click to open. citeturn9search0 HoldSpeak can preserve that for mouse spatial mode while using single tap on touch/pen, Enter for keyboard activation, and explicit Open verbs/context-menu items.

**Do not make dragging mandatory.** WCAG 2.2 requires a simple pointer alternative to functionality implemented through dragging unless dragging is essential. citeturn7search8 Every “drag meeting into drawer,” “drop source on Thread,” or “pull result onto Desk” operation therefore also needs a menu, picker or other single-pointer command.

**Do not make color, pixel art, or animation semantic dependencies.** HoldSpeak already uses multiple selected-state cues and icon-plus-text status, which is more faithful to the original guideline’s intent than a literal copy would be. fileciteturn29file0L2-L2 citeturn12view0

**Do not resurrect requester-heavy modal UX.** The modernized analogue of an Amiga requester should be HoldSpeak’s existing in-flow well/disclosure/window vocabulary. The current product canon explicitly forbids modal editing and uses inline confirmation components such as `ConfirmVerb`. fileciteturn13file0L2-L2 fileciteturn14file0L2-L2 Native browser/OS permission prompts are external platform surfaces and should not be emulated.

## Component system and interaction specification

### Atomic taxonomy as an overlay, not a rewrite

Brad Frost describes Atomic Design as a five-level mental model—atoms, molecules, organisms, templates and pages—not as a mandatory implementation architecture. Components should be considered both in isolation and in representative final contexts. citeturn14search0

That makes it ideal for **documenting** HoldSpeak, but renaming directories or forcing all existing components into new code folders would be counterproductive. The final SRS should add an `atomicLevel` classification to the design-system catalogue while leaving the current `desk/surface`, `desk/components`, `pages/cores`, etc. boundaries intact.

A useful HoldSpeak taxonomy is:

| Level | HoldSpeak meaning | Candidate existing species | Required contract |
|---|---|---|---|
| **Foundation** | Not technically an Atomic Design level; values from which all visual components derive. | color, type, space, elevation, bevel, z-layer, duration, easing, density, icon-cell tokens | semantic token, theme alias, minimum contrast, generation source |
| **Atom** | Smallest interactive/presentational unit with independent semantics. | `Button`, `VerbGlyph`, `StateChip`, `EgressChip`, `ProvenanceChip`, `MicButton`, checkbox/radio primitives, primitive token/chip | variant, size, tone, disabled/busy state, accessible name, events |
| **Molecule** | A small group of atoms implementing one coherent task. | `ConfirmVerb`, `EditInPlace`, `FilterTokens`, `StringGadget`, `CycleGadget`, object icon cell, menu row, search field, window verb cluster | value, state machine, keyboard contract, emitted actions |
| **Organism** | A distinct substantial region of an application. | `DeskWindowFrame`, `WorkMenu`, `SurfaceLedger`, `SurfaceFooter`, `SurfaceIdentity`, `SurfaceWings`, Dock, Exposé, Switcher, TaskResume list, drawer content | child composition, focus scope, loading/error/empty states, resizing behavior |
| **Template** | Layout that expresses a product posture independent of specific content. | Working surface, Reviewing surface, Configuring surface, Drawer template, Thread template, Meeting-review template, Info template | regions, responsive reflow, allowed organisms, focus entry, primary action placement |
| **Page** | Representative instantiated experience. | Spatial Desk, List Desk, Arrival, Presence; Speak window, Meeting window, Agents window, Settings window, Project window, Thread window | real data, roles, edge cases, screenshot fixtures, acceptance journey |

The current Agent Brief independently arrives at a similar notion through **postures**: working surfaces should emphasize the main action; reviewing surfaces should use dense material and inline verdicts; configuring surfaces should use grouped settings rather than generic forms. fileciteturn30file0L2-L2 Those postures should become the Template layer of the formal specification.

### Mandatory contract schema for every reusable component

Every component entry in the ultimate specification should use the same schema:

| Field | Required contents |
|---|---|
| **Name / level** | Canonical component and Atomic Design level |
| **Purpose** | One-sentence responsibility |
| **Composition** | Allowed children/dependencies |
| **Props** | Name, type, required/default, semantic meaning |
| **Visual variants** | Default, dense, primary, danger, selected, etc. |
| **Interaction states** | Rest, hover, focus-visible, active/pressed, selected, disabled, busy, success, warning, failure, unreachable |
| **Data states** | Loading, empty, partial, stale, error, offline/disconnected |
| **Events** | Semantic commands emitted, not incidental DOM details |
| **Keyboard** | Tab behavior, arrows, Enter/Space, Escape, shortcuts |
| **Pointer/touch** | click/tap, context, drag or resize behavior |
| **Accessibility** | native role, accessible name, ARIA only where necessary, live-region behavior |
| **Theming** | semantic tokens consumed; no literal visual values |
| **Motion** | trigger, property, duration token, reduced-motion equivalent |
| **Responsive** | container thresholds and alternate composition |
| **Localization** | expansion/wrapping constraints, truncation rule, locale formatting |
| **Test oracle** | unit, interaction, axe, screenshot and journey assertions |
| **Known consumers** | pages/templates using it |
| **Status** | canonical / provisional / legacy / deprecated |

The existing surface library already supplies much of this information. `EditInPlace`, for example, defines its value, commit callback, accessible label, disabled reason, multiline behavior and mic behavior; `ConfirmVerb` defines its resting/armed state and in-place destructive confirmation; `FilterTokens` defines its group semantics, state handling, active appearance and accessible naming. fileciteturn14file0L2-L2 The final spec should normalize these existing contracts rather than paraphrase them inconsistently.

### Recommended component state machine

A useful common lifecycle is:

```mermaid
stateDiagram-v2
    [*] --> Idle
    Idle --> Hover : pointer enter
    Idle --> Focused : keyboard focus
    Hover --> Pressed : pointer down
    Focused --> Pressed : Space/Enter
    Pressed --> Active : commit
    Pressed --> Idle : cancel
    Active --> Working : async command
    Working --> Success : completed
    Working --> Warning : completed with qualification
    Working --> Failure : rejected/failed
    Working --> Unreachable : transport unavailable
    Success --> Idle : settle
    Warning --> Idle : acknowledge/retry
    Failure --> Idle : retry/recover
    Unreachable --> Idle : connection restored
```

This does **not** mean every atom needs every state. It means the specification should use one shared vocabulary and explicitly declare the supported subset, which is already consistent with the repository’s closed `idle/active/working/success/warning/failure/unreachable` vocabulary. fileciteturn14file0L2-L2

### Interaction grammar

#### Selection and opening

Mouse spatial mode should preserve the currently documented Desk grammar:

`single click = select`  
`double click = open`  
`Shift/Ctrl/Primary-modifier click = extend/toggle selection where the surface supports multi-selection`  
`Enter = open selected object`  
`Space = select/toggle where semantically appropriate`  
`Escape = close the front transient/card or clear the current transient mode according to priority`

The single-click/double-click pattern is historically consistent with Workbench, where icons are selected first and opened by double-clicking. citeturn9search0 HoldSpeak already specifies mouse single-click selection, mouse double-click opening and single-tap touch opening. fileciteturn28file0L2-L2

A crucial specification detail is **selection scope**. Commodore advised keeping one current object or selected group at one selection level rather than simultaneously selecting unrelated levels. citeturn12view0 For HoldSpeak, that should mean:

- The Desk owns one world selection set.
- A window may own an internal selection set only while keyboard focus is inside that application.
- Menu/object commands identify which scope they target.
- Moving focus from the world into a window does not need to destroy the Desk selection, but only one scope may be the **command target** at a time.
- The active command context must be exposed visually and programmatically.

#### Windows and focus

A window must have one unique ID, one application/object identity, one persisted normal rectangle, one z-order entry and optional minimized/maximized status. Current code already follows that architecture. fileciteturn16file0L2-L2

The formal focus rules should be:

1. Opening a window brings it to the front.
2. Opening from an object records the invoker so focus can return there on close.
3. Focusing any meaningful element in a window activates that window.
4. Clicking a title/head safe area activates without modifying window content, preserving the original Amiga safe-activation principle. citeturn12view1
5. Closing returns focus to the opener when it remains valid; otherwise to the next frontmost window or Desk.
6. Minimizing moves focus to the next available application/window target.
7. Restoring brings the restored window front and moves focus predictably into it.
8. Keyboard focus may never end up visually hidden behind another authored HoldSpeak surface, aligning with WCAG 2.2 Focus Not Obscured. citeturn7search9
9. Ordinary Desk windows do **not** trap focus; only true transient composites such as menus/popovers may use bounded focus behavior. The existing Phase 96 accessibility decision already uses “focus without traps” for application windows. fileciteturn20file0L2-L2

Window verbs should remain one shared grammar:

`minimize · maximize/restore · close · snap · bring front · move/resize`

with mouse, touch and keyboard entrances sharing the same command implementation.

#### Keyboard/navigation

The final specification should define abstract shortcuts using a `Primary` modifier and resolve it per host/platform rather than hardcoding macOS glyphs into business logic.

Recommended canonical grammar:

| Command | Proposed shortcut | Notes |
|---|---|---|
| Global search / command shelf | `Primary+K` | Already central in HoldSpeak. |
| Application switch/open | `Primary+1…4` | Speak, Meetings, Agents, Settings; already a standing Agent Brief ambition. fileciteturn30file0L2-L2 |
| Close front window | `Primary+W` | Host/browser conflicts must be resolved by desktop host policy. |
| Minimize front window | `Primary+M` | Same command as window menu. |
| Cycle windows forward | `Ctrl+\`` or platform mapping | Already present in Desk window grammar. fileciteturn20file0L2-L2 |
| Cycle reverse | previous + `Shift` | MRU order. |
| Exposé/window overview | configurable system shortcut | Existing implementation already has an Exposé concept. fileciteturn16file0L2-L2 |
| Open context menu | context-menu key or `Shift+F10` | Enables right-click functionality from keyboard. |
| Open selected object | `Enter` | Same semantic command as double click. |
| Rename/edit current value | `F2` or explicit registry verb | Must use `EditInPlace`. |
| Cancel current transient operation | `Escape` | Menu → drag → inline editor → front transient in defined priority. |
| Shortcut map | `Primary+/` | Agent Brief already identifies a drawn shortcut sheet as desired OS territory. fileciteturn30file0L2-L2 |

The menu itself should implement a complete ARIA menu keyboard model: arrow-key traversal, activation, submenu handling, Escape dismissal and focus return. The repository already records that its current menu implements the Radix keyboard **pattern** without importing Radix primitives. fileciteturn20file0L2-L2

#### Drag and drop

The current HoldSpeak drop model is one of its strongest design choices: allowed source-target combinations live in `dropMatrix.ts`; viable targets visibly light; a cursor-adjacent verb names what release means; and potentially consequential model actions are not triggered merely by a drop but instead receive held input awaiting an explicit run action. fileciteturn28file0L2-L2

The ultimate specification should extend that grammar to five stages:

```text
candidate → armed → dragging → over-valid-target → commit/cancel
```

Each stage should specify pointer imagery, source state, target state, live announcement, cursor verb, cancellation behavior and whether the source returns home.

Every drag operation must additionally have:

- an Object/context menu command;
- a keyboard-accessible destination picker or equivalent;
- a simple non-drag pointer path.

That last requirement follows directly from WCAG 2.2 SC 2.5.7. citeturn7search8

The original Amiga’s ability to cancel window drag using the alternate mouse button is historically interesting, but HoldSpeak should modernize the principle to **Escape cancels any in-progress drag**, while pointer release commits only over an explicitly valid target. The original guide similarly emphasized actions on release so that users can move away and cancel before commitment. citeturn12view0

#### Modal and dialog rules

Product-level modal dialogs should remain prohibited.

Use, in priority order:

`inline edit → disclosure/well → dedicated Desk window → OS-native system prompt`

Destructive actions should use HoldSpeak’s existing in-place two-stage `ConfirmVerb`, not a confirmation modal. fileciteturn14file0L2-L2

A “dialog” in the SRS should mean one of two precisely named things:

**Desk window** — movable, nonmodal, participates in normal z/focus/window lifecycle.

**Platform dialog** — unavoidable OS/browser surface such as file selection, microphone permission, code signing, secure credential selection, etc.; owned by the host rather than rendered as fake HoldSpeak chrome.

This distinction prevents an agent from satisfying a requirement for “dialog rules” by reintroducing modal SaaS patterns that the repository explicitly rejected.

#### Motion and microinteractions

Commodore treated visual response as an essential confirmation that input was accepted. citeturn12view0 HoldSpeak’s design canon turns that into a stronger modern rule: motion should communicate state changes rather than decorate idle UI, and reduced motion must eliminate nonessential animation. fileciteturn13file0L2-L2

The specification should define named motion primitives rather than one-off animations:

| Motion | Meaning | Reduced-motion behavior |
|---|---|---|
| **Press** | control accepted pointer/key down | state change only |
| **Select** | object became current | selected imagery immediately |
| **Window open/close** | spatial relationship to source object | appear/disappear without travel |
| **Minimize/restore** | movement between work surface and Dock | instant state transition |
| **Snap ghost** | previews final window geometry | static preview |
| **Drop affordance** | target is valid and names operation | static selected target + verb |
| **Materialize** | newly created object now exists | immediate appearance with `NEW` state |
| **State settle** | working → outcome | chip/text state change only |
| **Wing/posture switch** | same application changed work posture | instant content switch |
| **Inline edit commit** | presented data became new data | text update only |

The current canon’s guidance of at most four named motion moments per face is a useful complexity ceiling. fileciteturn13file0L2-L2

### Responsive behavior

The correct conceptual translation of Amiga’s “design against the least capable practical screen” is **container-first resilience**, not viewport-specific retro emulation. Commodore recommended designing so windows continued to work at constrained resolution and honoring user-selected font and resolution settings. citeturn12view0turn12view1

HoldSpeak already uses `@container surface` as the interior reflow authority and explicitly discourages route/core-specific viewport media queries. fileciteturn14file0L2-L2

The specification should define at least these presentation classes:

| Container condition | Behavior |
|---|---|
| **Wide desktop** | Free spatial Desk, overlapping windows, full menubar + Dock, multi-column interiors where valuable |
| **Standard desktop/laptop** | Same OS grammar, denser content, avoid unnecessary multi-column interior layouts |
| **Narrow window** | Organisms stack; row metadata wraps or folds; wings stay within head |
| **Compact/phone** | List mode may lead at high object density; application windows become sheet-like/full-height compositions; direct spatial arrangement is secondary |
| **Large-text/high zoom** | Reflow rather than horizontal clipping; essential controls remain reachable |
| **Reduced motion** | Same semantic states, instantaneous transitions |
| **High contrast/forced colors** | status/selection still comprehensible without authored color dependency |

The repository already defaults compact high-density desks to list mode beyond an explicit object threshold while retaining a saved user choice, demonstrating the right principle: responsive behavior may change presentation defaults, but it must not silently erase user preference. fileciteturn23file0L2-L2

## SRS architecture, requirements, and technology decisions

### Functional requirement structure

The final specification should use RFC-style normative language and trace every requirement to design, implementation and verification artifacts.

A strong initial requirement set is:

| ID | Functional requirement | Acceptance intent |
|---|---|---|
| **FR-DESK-001** | The system SHALL expose the Desk as the primary operating surface. | Product capabilities do not spawn independent competing shell architectures. |
| **FR-DESK-002** | The Desk SHALL provide spatial and semantic/list representations of the same objects. | Full task parity for users who cannot or do not want to operate spatially. |
| **FR-OBJ-001** | Each Desk primitive SHALL have one registry-defined object kind, visual representation and supported verb set. | No feature-local invention of object semantics. |
| **FR-OBJ-002** | Selection SHALL be visible through at least two non-color-only cues. | Selected state remains perceivable under grayscale/high-contrast conditions. |
| **FR-OBJ-003** | The mouse grammar SHALL support select then open/action; equivalent keyboard and touch operations SHALL exist. | Preserve object-action without input-device dependence. |
| **FR-WIN-001** | Every product window SHALL use the common window lifecycle. | Common move/resize/focus/minimize/maximize/close behavior. |
| **FR-WIN-002** | User-arranged window geometry and order SHALL survive the defined workspace persistence lifetime. | Arrangement is treated as user-owned state. |
| **FR-WIN-003** | Opening/closing SHALL preserve a deterministic focus-return relationship. | Keyboard users do not become stranded. |
| **FR-WIN-004** | Window state SHALL be migrated/clamped when display geometry changes. | Persisted layouts remain recoverable across monitor/viewport changes. |
| **FR-MENU-001** | All menu faces SHALL derive labels/availability/shortcuts from the canonical verb registry. | No divergent menu vocabulary. |
| **FR-MENU-002** | An unavailable menu capability SHALL remain discoverable when appropriate and SHALL expose the reason it cannot run. | Amiga-style ghosting with modern explanatory semantics. |
| **FR-CMD-001** | Every user action with side effects SHALL dispatch a semantic command rather than embedding side effects in view components. | GUI, keyboard and future desktop host use the same behavior. |
| **FR-DND-001** | Drag targets SHALL be declared through contract data. | No component-local source/target matrices. |
| **FR-DND-002** | Drag functionality SHALL have an equivalent non-drag pointer operation. | WCAG 2.2 compliance. citeturn7search8 |
| **FR-DND-003** | A drop SHALL state the operation before commitment. | Cursor/target verb provides consent context. |
| **FR-AI-001** | A drag/drop gesture SHALL NOT silently cause model execution where an explicit run decision is required. | Preserve current HoldSpeak consent grammar. |
| **FR-VOICE-001** | Text-entry-capable product fields SHALL participate in the defined voice-input law unless explicitly exempted. | Voice remains first-class rather than a separate feature. |
| **FR-STATE-001** | Long-running operations SHALL expose truthful working/outcome states. | No fake deterministic progress. |
| **FR-DESK-003** | Destructive confirmation SHALL occur in-world using the canonical confirmation interaction rather than application-modal UI. | Preserve no-modal product grammar. |
| **FR-INFO-001** | Object Info SHALL be contract-derived and SHALL expose only properties backed by real data/update contracts. | No decorative property panels. |
| **FR-SEARCH-001** | Global search/command access SHALL reach every supported application/tool/object class. | One launcher/search grammar. |
| **FR-HOST-001** | A desktop host SHALL expose platform features through a bounded typed bridge. | Renderer UI remains host-independent. |
| **FR-HOST-002** | The web product SHALL remain functional without a desktop wrapper except for explicitly native-only capabilities. | Desktop is an adapter, not a rewrite. |

### Nonfunctional requirements

#### Accessibility

The baseline should be **WCAG 2.2 AA**, with deliberate AAA-level choices where they cheaply strengthen desktop usability. W3C recommends WCAG 2.2 as the current conformance target; relevant additions include Focus Not Obscured, Dragging Movements, and Target Size Minimum. citeturn7search0

Proposed acceptance requirements:

- All product work is operable by keyboard.
- Spatial manipulation has semantic alternatives.
- Pointer targets meet WCAG 2.2 AA sizing/spacing; W3C defines the default minimum as 24×24 CSS px with specified exceptions. citeturn7search6
- Primary/high-frequency touch actions should target the stricter 44×44 guidance where layout permits; W3C identifies 44×44 CSS px as the enhanced target size criterion. citeturn7search11
- Focus is visible and not hidden behind authored UI.
- Selection and status do not rely on color alone.
- Screen-reader state announcements occur on meaningful transitions rather than continuous motion.
- Spatial Desk behavior has a semantic DOM/list representation with equivalent commands.
- Browser zoom and enlarged text do not cut off critical controls.
- Reduced-motion preference results in functionally equivalent instantaneous states.
- All generated keyboard shortcuts have programmatic labels and visible discoverability.

Current HoldSpeak already has a substantial foundation for these requirements, including axe-core, Testing Library, explicit ARIA patterns, roving tabindex, and reduced-motion rules. fileciteturn11file0L2-L2 fileciteturn14file0L2-L2

#### Performance

The specification should define budgets as **acceptance thresholds**, not vague “fast enough” adjectives. Recommended initial budgets for benchmark hardware should include:

| Metric | Proposed target |
|---|---:|
| Local press/select visual feedback | next rendered frame |
| Drag/resize interaction | no sustained frames exceeding a 60 Hz frame budget during normal single-window manipulation |
| Window focus/z-order change | one interaction frame, excluding requested content loading |
| Menu/context-menu opening | perceptually immediate after invocation |
| First usable Desk after shell/data prerequisites | explicit benchmark to be measured and frozen during baseline phase |
| Runtime bus handling | no unbounded render cascade per incoming frame |
| Idle CPU | no decorative continuous animation that materially keeps the application busy |
| Bundle growth | existing bundle gate retained; any threshold change requires reasoned ADR |
| GL object density | tested at representative normal, heavy and pathological fixtures |
| Memory after repeated window open/close | bounded; no retained window/listener growth |

The repository has historical evidence that its assembled material/window family passed a performance “storm” with an 8.3 ms median and 10.0 ms p95 in Phase 96, demonstrating that performance is already treated as a measurable design property. fileciteturn20file0L2-L2 The final agent should rerun and baseline current-main numbers rather than assume those July 2026 measurements remain current.

#### Localization

The specification should require:

- all visible user-facing labels/messages to come from a localization-capable source rather than being scattered literals;
- no localization of protocol identifiers, registry IDs or stable command IDs;
- locale-sensitive date, time, number and measurement formatting;
- expansion fixtures at +30%, +50% and pathological strings;
- testing with long compound nouns;
- Bidi/RTL analysis even if first rollout remains en-US;
- accessible names localized with visible labels;
- keyboard shortcut notation adapted to platform/locale where necessary;
- icon-only controls never relying on English tooltip text as their sole accessible identity.

The historical guide explicitly warned that English-to-German text could grow roughly 30–50% and recommended centralizing translatable strings rather than scattering text throughout applications. citeturn12view0 This is one of the most directly transferable principles from the original Amiga documentation.

#### Theming

The design token graph should be formalized as:

```text
primitive tokens
    ↓
semantic roles
    ↓
component tokens
    ↓
theme aliases
    ↓
renderers: DOM + WebGL + optional native host chrome
```

The current HoldSpeak design system already uses a three-layer token approach and generates both CSS and TypeScript representations. fileciteturn20file0L2-L2

Required themes should be treated separately from “skins”:

- **Signal Dark** — current default.
- **High Contrast** — functional accessibility variant.
- **System/automatic** — selects supported light/dark semantics once both exist.
- **Signal Light** — future semantic parity target.
- Optional **Workbench Tribute** appearance may change palette/material intensity only; it must not change interaction semantics.

The repo currently explicitly keeps dark-only behavior while preserving the semantic layer as the future light-theme attach point, so the final SRS should make theme expansion a scoped roadmap item rather than pretending it already exists. fileciteturn19file5L70-L82

#### Reliability and recoverability

Workspace persistence should be versioned and tolerant of:

- deleted/unknown window IDs;
- application renames;
- display-size changes;
- stale rects;
- corrupt local state;
- rollout/rollback across schema versions.

Backend data must never depend on successful workspace persistence. Losing local layout may reset arrangement; it must not lose Notes, Meetings, Threads or other hub records.

#### Security

The desktop host must expose the **minimum native authority needed per capability**.

For Electron, official guidance includes context isolation, sandboxed renderers, restricted navigation/window creation, validating IPC senders, avoiding Node integration in web content and exposing only narrow APIs across `contextBridge`. citeturn6search0turn6search3turn6search13

For Tauri, capabilities define which permissions a given window/webview receives, and the runtime authority verifies origin, capability and scope before a command is invoked. citeturn6search6turn6search8

The SRS should therefore describe host interfaces such as:

```ts
interface DesktopHost {
  readonly kind: "web" | "tauri" | "electron";

  showOpenDialog?(request: OpenDialogRequest): Promise<FileHandleRef[]>;
  showSaveDialog?(request: SaveDialogRequest): Promise<FileHandleRef | null>;

  registerGlobalShortcut?(
    commandId: CommandId,
    accelerator: string
  ): Promise<void>;

  showNotification?(notice: SystemNotice): Promise<void>;

  setTrayState?(state: TrayState): Promise<void>;

  revealPath?(opaqueRef: LocalFileRef): Promise<void>;
}
```

The renderer must **not** receive arbitrary filesystem, shell or process APIs.

The repository already has concrete window and Desk models, but the ultimate specification should publish portable schemas rather than make TypeScript implementation the only source of truth. Current examples such as `PanelRect`, `WindowInstance`, `DeskView` and `ZoneViewPref` are strong starting points. fileciteturn23file0L2-L2

For every model the SRS should label:

**persistence** — ephemeral, session, workspace, hub

### API and integration specification

The final SRS should generate a **surface → capability → API → event → receipt** matrix rather than documenting HTTP routes independently.

Example:

| Surface/verb | HTTP/API | Runtime event | Local state | Receipt/egress |
|---|---|---|---|---|
| Open Meeting | read meeting endpoint | optional live meeting frames | window geometry only | none |
| Start recording | hub recording route | runtime activity | recording projection | hardware/local boundary |
| File object into drawer | membership route | refresh/record event | object position remains separate | hub mutation |
| Run Workbench | capability/run API | model/run frames | working state | model placement + receipt |
| Rename drawer | update route | refreshed object state | editing flag ephemeral | hub mutation |
| Desktop open file | host bridge | import progress on runtime bus | optional source window | local filesystem boundary |

The Web architecture already mandates typed HTTP through one client and a single product WebSocket connection. fileciteturn18file0L2-L2 A desktop integration should preserve those boundaries and add a separate `DesktopHost` adapter rather than bypassing them.

### Candidate framework and library tradeoffs

#### Desktop shell

| Option | Strengths | Costs/risks | HoldSpeak fit |
|---|---|---|---|
| **Web/PWA only** | Zero new native runtime; exactly current architecture | Cannot reliably supply every desired native desktop feature such as global shortcuts/tray/filesystem integration across platforms | Keep as mandatory baseline and fallback |
| **Tauri 2** | Uses HTML in OS WebViews with a Rust core; explicit permissions/capabilities; does not bundle its own WebView. citeturn8search8turn6search21 | Adds Rust/native build expertise; system WebView creates more cross-platform rendering variability | **Strong thin-host candidate** if package footprint/security boundaries outrank rendering uniformity |
| **Electron** | Bundles Chromium + Node and therefore offers a stable web rendering target across supported desktop OSes. citeturn8search0turn8search2 | Bundled Chromium/Node adds another runtime and demands disciplined IPC/security maintenance; official guidance is extensive. citeturn6search0 | **Strong thin-host candidate** if exact Desk rendering parity and JS expertise outrank footprint |
| **Native rewrite** | Maximum platform integration | Duplicates the mature React Desk, design system and interaction model; extremely high semantic drift risk | Reject for this objective |

**Recommendation:** specify the desktop boundary before choosing the container. Build a small Tauri and Electron host spike against the **same production web build** and score them on startup, install/update pipeline, signed packaging, global shortcut behavior, tray integration, microphone/global-hotkey coexistence, native dialogs, visual rendering parity, security review complexity, resource use and developer skill cost.

This is particularly important because existing HoldSpeak design decisions previously declined a Tauri or Electron shell in other scopes. The new user-level requirement changes that assumption, so the wrapper choice must be an explicit new ADR rather than an accidental dependency. fileciteturn34file0L2-L2 fileciteturn31file0L1-L10

#### UI primitive strategy

| Candidate | Benefit | Conflict/cost | Recommendation |
|---|---|---|---|
| **Existing HoldSpeak Surface/Signal system** | Already tokenized, Workbench-specific, tested, repository-canonical | Some legacy violations and missing species remain | **Primary choice** |
| **React Aria Components/hooks** | Unstyled accessible React primitives; accessibility, internationalization and cross-input behavior are built into the library. citeturn8search1 Its drag/drop support includes keyboard and screen-reader operation. citeturn6search1 | Introduces a second interaction abstraction and may conflict with hand-owned Desk semantics | Consider only for a new difficult composite after an ADR; skin through existing HoldSpeak components |
| **Radix Primitives** | Accessible unstyled primitives with established keyboard patterns. citeturn6search22 | Repo has already explicitly chosen “patterns yes, primitives no.” fileciteturn20file0L2-L2 | Do not adopt wholesale without overturning the existing ADR |
| **MUI/Chakra/full component kit** | Broad prebuilt UI coverage | Second visual/state vocabulary; encourages generic app/dashboard composition contrary to existing product canon | Reject as product-level foundation |
| **Tailwind/shadcn replacement** | Utility speed and ecosystem | Repository design-system documentation explicitly records that the Tailwind/shadcn stack was not adopted. fileciteturn19file5L70-L82 | Reject as architectural replacement |
| **Custom components for everything** | Maximum aesthetic control | Reimplements difficult accessibility mechanics repeatedly | Continue only under current rule: recurring patterns become library species with explicit tests |

The best modernization path is therefore **not** “replace HoldSpeak controls with React Aria.” It is to permit a HoldSpeak component to use a headless accessibility primitive internally when there is a demonstrable need and no conflict with the existing semantics. That keeps the public design-system contract stable.

## Risks, technical debt, testing, and rollout

### Risk register

| Risk | Evidence | Severity | Mitigation |
|---|---|---:|---|
| **Agent treats assignment as greenfield redesign** | Exact Workbench vision already shipped in Phase 105. fileciteturn27file0L2-L2 | Critical | First deliverable is a repo-to-spec traceability census; no new visual proposal until existing law is mapped. |
| **Existing canon documents overlap or conflict** | Constitution, Agent Brief, Design System, UX Canon, Desk Grammar and Surface contract all govern different layers. | High | Produce source hierarchy + conflict ledger; every conflict resolved explicitly. |
| **Implementation is more precise than documentation** | Phase 105 names TypeScript-only drag thresholds, layout math, motion and menu behaviors as spec debt. fileciteturn27file0L2-L2 | High | Extract them into portable normative contracts before new platform work. |
| **Workbench becomes decorative nostalgia** | Original source focuses on behavior, consistency and feedback, not decorative retro styling. citeturn12view0 | High | Require rationale mapping each retro-inspired choice to a job/usability principle. |
| **Spatial UI excludes keyboard/motor users** | Dragging is central to the metaphor; WCAG 2.2 requires alternatives. citeturn7search8 | Critical | Semantic list view, command registry alternatives, keyboard destination pickers. |
| **WebGL world is less semantically accessible than DOM** | Spatial world is Pixi/WebGL while windows are DOM. fileciteturn18file0L2-L2 | High | Treat semantic/list representation as equal product surface; maintain state/verb parity tests. |

### Test architecture

The final specification should define five test layers.

**Static contract tests** verify design tokens, vocabulary, component imports, prohibited raw controls, prohibited modal roles, registry completeness, no direct fetch/socket bypass and schema compatibility. Much of this already exists. fileciteturn18file0L2-L2

**Component interaction tests** should exercise every supported state and keyboard path with Testing Library/user-event, including focus return, selected/disabled/working state, menu traversal, compact reflow and reduced motion. The current package already includes these libraries plus axe-core. fileciteturn11file0L2-L2

**Accessibility tests** should combine axe with behavioral assertions. Axe alone cannot prove correct window focus, useful reading order or complete drag alternatives.

**Visual/regression rigs** should render canonical fixtures at wide desktop, narrow desktop, 393-ish compact, large text, pseudo-localized copy, reduced motion and high contrast. Existing HoldSpeak process already uses 1440 and 393 screenshots and treats visual review as part of UI acceptance. fileciteturn13file0L2-L2

**Real journey/E2E tests** should verify representative user jobs through the production FastAPI/React bundle and real runtime bus. Current CI already has critical journeys, integration testing, live bus gating and browser E2E on macOS plus Linux smoke coverage. fileciteturn21file0L2-L2

Desktop builds add a sixth layer:

**Host-contract tests**, executed against Tauri/Electron adapters, covering denied permissions, global shortcut lifecycle, navigation prevention, native file dialogs, app relaunch/workspace restore, updater rollback, microphone/hotkey coexistence and renderer compromise assumptions.

### Rollout strategy

The wrapper and expanded design contract should not land as one flag-day rewrite.

**Stage A — spec only.** Freeze the normalized design/SRS baseline and trace every normative statement to code or an explicitly open requirement.

**Stage B — web conformance.** Make the existing web Desk conform to that spec. Do not start desktop implementation while fundamental requirements are marked “unknown.”

**Stage C — host abstraction.** Introduce `DesktopHost` with the pure Web implementation as the null/default adapter.

**Stage D — internal desktop preview.** Run one chosen host against the production bundle with native capabilities disabled by default.

**Stage E — capability-by-capability enablement.** Tray, global shortcuts, system notifications, file integration and updater each receive their own permission/security tests.

**Stage F — opt-in beta.** Keep browser/web operation as recovery and parity reference.

**Stage G — default desktop distribution**, only after critical journey parity, crash/relaunch behavior, upgrades and workspace migration have been proven.

This preserves the existing “web Desk is the spec” principle while satisfying the new requirement for a desktop product.

The critical-path skills are not “generic frontend developer” alone. The effort needs:

**A senior React/design-systems engineer** who can work inside an existing tokenized system instead of importing another kit.

**A Pixi/WebGL interaction engineer** for the world/object layer and gesture performance.

**An accessibility specialist** comfortable with composite desktop-like widgets, spatial alternatives and screen-reader testing beyond axe.

**A product interaction designer** capable of producing high-fidelity, content-realistic 1440/393 artboards and reasoning in object-action/window metaphors rather than conventional dashboard components.

QUALITY BAR

The final specification fails if:
- it could describe a generic SaaS dashboard;
- it ignores existing HoldSpeak code;
- it creates a second UI architecture;
- it treats Amiga as visual decoration only;
- it leaves interaction details to developer interpretation;
- it says "accessible" without concrete behavior/tests;
- it requires drag without alternatives;
- it introduces modal workflows casually;
- it introduces a second command/state model;
- it lacks compact layouts;
- it lacks real-content mockups;
- it lacks measurable acceptance criteria;
- it lacks source citations;
- it lacks a traceability matrix;
- it proposes Electron or Tauri without a bounded host abstraction;
- it does not name the existing technical debt and standing remainders.

FINAL DECISION PRINCIPLE

When deciding whether a design belongs, ask:

"Would a person accustomed to a real desktop environment understand what this
object is, what is selected, what can be done to it, what is happening now,
where the result went, and how to accomplish the same job without a mouse?"

If the answer is no, the specification is not finished.

The target is not an Amiga museum piece.

It is HoldSpeak as a genuine personal operating surface:
Workbench's object clarity, Intuition's interaction discipline, modern
accessibility, HoldSpeak's voice/AI capabilities, and one coherent command and
state model across web and desktop.
