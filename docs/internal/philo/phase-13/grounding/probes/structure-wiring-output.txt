  utility/catalog state, but their Tuesday value must be demonstrated before

* Reachability is not the same as useful work. Grouped rows reach Go/Launch;
  ungrouped rows rely on deep routes or explicit handoffs. Static source cannot
  measure time-to-first-useful-pixel, stale data, or whether a core's fallback
  paints; faces must walk those paths.
* One static handoff is broken: `BriefView.tsx:490` calls
  `openSurfaceOr("people", "/people", relationship_id)`, but the canonical

  absent; `App.tsx:68` wildcard navigation lands at `/`. This is a J1 → J3
  dead handoff found statically, not observed in a browser. Do not silently
  count the brief's “Open person” as reachable.

Window persistence and loss:

* The sole workspace key is `hs.desk.workspace.v1` (`workspaceStorage.ts:8-25`)
  with `windowsById`, saved panel rectangles/order/max, zone window IDs and
  zone view preferences. The parser accepts only `kind: "surface"`,
  `persistence: "workspace"` instances (`:61-76`) and compositor startup
  filters them against the current surfaced action/window maps
  (`compositorSlice.ts:43-57`). Stale rows are ignored rather than shown.
* A surface open creates a normalized instance and focuses it
  (`compositorSlice.ts:234-256`); close removes the instance and retires its
  panel (`:257-264`). The rectangle can remain in saved panel geometry until
  reset because `retirePanel` removes order only (`:312-317`) and
  `saveDeskWorkspace` writes only IDs in `panelSaved` (`workspaceStorage.ts:131-149`).
  This means close loses the open document state, while a saved geometry may
  survive. A reload restores open surfaced instances, order, max state and
  saved geometry, but not unsaved pullouts, Ask state, transient palette or
  shortcut state (`chromeState.ts:1-24`), and not the five factory window arrays
  as `windowsById` records (they have their own store state/origin).
* This is a credible Workbench base: one frame, a normalized surface registry,
  z-order, drag/resize, min/max and persisted rectangles. A Workbench-grade
  next seam is explicit workspace “screens”/named layouts and a durable
  document identity for object windows; snap/Expose/Switcher are currently
  compositor UI, not a saved screen model. Do not add a second persistence
  store before the owner sees a Tuesday loss case (Tenets 1, 3, 6).

6. Hard-delete seams and park requirement
-----------------------------------------

Meetings have a direct hard-delete path: History calls DELETE and renders
`DELETED` (`web/src/pages/cores/HistoryCore.tsx:456-465`); the route invokes
the service (`holdspeak/web/routes/meetings/crud.py:140-152`); the DB executes
`DELETE FROM meetings` (`holdspeak/db/meetings.py:1061-1067`), with related
rows subject to schema cascades. There is no park/archive branch in this path.

Workbench behavior has two different meanings under one DELETE vocabulary:

* `DELETE /api/workbenches/{id}` is exposed by the route
  (`holdspeak/web/routes/primitives/workbenches.py:90-100`) and service
  (`workbench_service.py:159-167`), but the DB method updates `deleted=1`
  (`db/workbenches.py:154-164`): parent workbenches are retained/soft deleted.
  A separate `purge()` hard DELETE exists (`:166-169`).
* `DELETE /api/workbenches/{id}/items/{item_id}` is wired from the Workbench
  window (`web/src/desk/api.ts:900-908`) through route/service
  (`workbenches.py:134-144`, `workbench_service.py:218-225`) to
  `DELETE FROM workbench_items` (`db/workbenches.py:295-301`). Workbench
  items are hard-deleted unless claimed (claimed items are refused).

This conflicts with the owner standing ruling in `AGENTS.md`, “Never delete;
park instead.” Highest-cost findings are therefore J2 (meeting record loss) and J4
(project/workbench history loss), Tenets 3, 5 and 7, Article V/VI. Smallest
seams are: replace History's DELETE action with a park/retire verb and a named
receipt; add an item park state/route at the existing workbench item route,
then keep purge as an explicit maintenance boundary. A static audit cannot
claim those routes exist today.
