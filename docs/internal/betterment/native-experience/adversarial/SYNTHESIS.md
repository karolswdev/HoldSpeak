# What the 47 adversarial reviews change

Baseline: main `55572802181d6a8045f6d27e3c722aaf5694dbbd`, 2026-10-23.
All 47 family audits received a fresh independent reviewer and root
reconciliation. [The index](README.md) links every record and its correction.

The original inventory covers the declared source corpus, but does not close
the whole jobs. The reviews return **32 RATIFY-WITH-CONDITIONS and 15
DO-NOT-RATIFY** on audit sufficiency as implementation briefs. These are not
47 production readiness verdicts. There are **204 proposed acceptance
challenges**, not 204 executed tests. The families include framework behavior,
a proposed explorer workload and disabled Presence as well as active apps.

## The three questions

**Are we considering the whole use case?** The original records often stopped
at a host, a button or a broad shared-behavior code. The reviews now trace
entry, identity, useful outcome, interruption, recovery and return. Important
variants were missing: two connected accounts, an older-than-first-page
meeting, first words before a note exists, a parent run that outlives Stop,
and a settings edit after returning to a hidden tab. Declared source coverage
still cannot establish every provider, device, future job or live state.

**Where should we converge?** Existing contracts already provide much of the
foundation. Today and Needs share their snapshot, rank and NeedRow. Active
notes use the Thought writer and CodeMirror caret insertion. Ask keeps turns
as threads. Send retains frozen bytes and a replay key. Agent results have
launch/turn identity, New/seen state and ResultBlock. The compositor owns front
window authority. Preserve those seams and extend them through real consumers.

**Are we pleasing the user?** That is not established. The owner's repeated
rejection of appearance remains the live product judgment. Idle captures and
passing geometry floors cannot overrule it. A complete, satisfying task needs
a quick first move, readable material, a clear intended target, predictable
keyboard/focus behavior, truthful feedback and an easy return. Those qualities
must be designed and observed together. More guards alone do not produce
craft; neither do a new icon set or a component catalogue.

## Verification and limits

Root read all 47 records, checked material source claims, reconciled conflicting
recommendations, and checked the exact family set, required sections, valid
source anchors and convergence identifiers. Root corrections deliberately
removed claims contradicted by existing live cleanup guards, actual-model
labels, turn/seen fields, common rename support, automatic summary policy,
owner no-Keep decisions and parked routes. Current behavior is evidence, not
a reason to preserve surprising keyboard/menu target differences.

Beyond the executed publication checks recorded in the index, the one
review-specific experiment was the Settings fixture and its control, under
the test lock with isolated HOME. No owner configuration, calendar,
microphone, account, provider send, terminal control or native host was used
by the reviewers. Existing captures are explicitly scoped visual references.
No live cross-product walk, assistive-technology acceptance, performance
baseline, portable-client validation or owner aesthetic acceptance is claimed.
Delivery checks for publishing these records are recorded in the index.
