## Goal

The owner works in a project room. He makes a project, puts a milestone and a risk in it, sees what needs him, lets the steward run and draft his update, publishes it in the Room, copies the finished text to send it himself, and marks it delivered — from the Room's face or from an MCP client that knows only the catalogue. An agent he grants a bounded project delegation can do the delegated part. The Room, its sources (the connectors) and the steward reach one declared operation each, bound to the hub's services, as Phase 7 did for notes, zones and decisions. The Room's face shows what the hub holds. Plus one bounded story of desk debts from the Phase 8 ledger. The product sends nothing: delivery is his act, recorded when he confirms it (Q0 ruling).

### The admission table (Q1 (a), every in-scope identity)

"Admitted" = one kernel operation before it acts and one terminal receipt, on both transports, with refusal receipts (Phase 7 R2). "Exempt" = the row itself is a plain edit or a read (Article XI.5); an exempt row adds no operation of its own, but it may still carry a lower-level effect that keeps its own admission (a model draft's `inference.invoke`). Admission is by effect, never by name: a "list" or "count" that probes a provider is admitted, or is chartered as a cached read. A row with an existing lower-level admission keeps it and is not admitted twice: the existing operation becomes a child of the row's operation, or the row is admitted by that operation alone (the steward beat and story 01 decide which, per row, and record it). An AGENT calling an admitted row is refused `project_delegation_required` (then `_expired`, `_revoked`, the Phase 7 order, `holdspeak/kernel/desk.py:17-18`, `:44-45`) with a refusal receipt, unless a LIVE project grant for that agent and that project names the operation ("The project delegation grant"); with the grant it executes, and its receipt names the delegation. Exempt rows and reads keep today's palette behaviour.

### Delivery by copy and confirm (the Q0 ruling)

- **Copy:** the face's existing Copy (`UpdatePosture.tsx:580-587` → `useUpdateController.ts:163-179` → `GET /api/updates/{id}/markdown`, `project_updates.py:195`) gives him the finished Markdown; over MCP the finished text is the published update's `body_md` from `project.list_updates`. A read; nothing leaves the machine through the product, so there is no egress badge — the canvas says so by showing none.
- **Confirm:** a **published** update always offers **Mark delivered** — before and after earlier deliveries, not only in the two seconds after Copy (the Copy feedback expires, `useUpdateController.ts:169`; no clipboard state is stored), so he can copy, leave to deliver, return and confirm (R4-3). The update's footer offers **Mark delivered** (the library Button) with an optional inline **To** field (free text: "Priya", then "the Tuesday staff channel"). Each confirmation adds one delivery row. No modal (UX-CANON §A.4); canvas first, both widths (§A.2).
- **The record (Tenet 1, minimal; the owner's "Several per update"):** one small additive table, `project_update_deliveries` (`id TEXT PRIMARY KEY`, `update_id` → `project_updates.id`, `project_id`, `delivered_at TEXT` = the owner's confirmation time, `delivered_to TEXT` nullable free text, `operation_id TEXT` = the kernel operation that admitted the mark; an index on `update_id`), created by the schema's additive reconcile (`holdspeak/db/reconcile.py:655` adds missing tables; the owner's "migrations stay minimal"). **No write to `project_updates` at all**: the published-update guard (`holdspeak/db/updates.py:244-250`) is untouched. Each mark appends one row; a draft is refused `update_not_published`; a row is never edited or deleted. `project.mark_update_delivered` (MCP) and `POST /api/updates/{id}/delivered` (HTTP) reach one declared operation (story 02, with its admission; story 01 creates the table and the read-backs — R4-2).
- **Idempotency (Codex Astra r5):** one logical confirmation keeps its `command_id` through double-clicks and retries. A repeat with the same principal, key and payload returns the original delivery — its row, `delivered_at`, operation and receipt — through the kernel's replay (operations are found by principal and idempotency key, `holdspeak/kernel/journal.py:123-128`); the same key with a changed payload is refused `idempotency_conflict`; a deliberate further delivery, even to the same recipient, uses a new key. **Omitted key:** the face always mints one key per confirm gesture (one press of Mark delivered, kept across its retries); an MCP call without `command_id` is a new delivery, and the tool description says so.
- **The operation link and persistence (Codex Astra r5):** `operation_id TEXT NOT NULL UNIQUE REFERENCES kernel_operations(operation_id)`, supplied by the execution context, never by the caller; `project_id` is derived from the stored update, never from the arguments; no cascade delete (a delivery row and its operation outlive any later change). The delivery insert, the operation's terminal state and its receipt are written in **one transaction** through the existing machinery (`holdspeak/kernel/journal_atomic.py:83`, `transition_and_receipt`), so no row exists without its receipt and no receipt without its row.
- **A mistaken delivery** is recorded, not rewritten: the face lists every delivery with its time and To, and a wrong one stays in the history (he can add the right one). Adding the correct delivery does not retract or mark the wrong one, and DELIVERED ×N counts both — a known limitation the canvas shows faithfully. "Undo a delivery" is parked on the BACKLOG.
- **Read back:** `project.list_updates` and the Room read's updates section (the F6 repair) carry each update's `deliveries` list (every row, oldest first); the update shows its delivery history, and the update list shows a DELIVERED chip — the copy-and-confirm canvas decides its form (DELIVERED ×N, or the latest time and To); RECEIPTS shows each delivery write.
- **Admission and authority:** each mark admitted with its own operation and receipt (the table's rule: it cannot be undone). `delivered_at` is the time he confirmed; the receipt proves he recorded the confirmation, not that a recipient received anything (R4-2); owner-only — it records the owner's own act, so the project grant never names it and an agent is always refused `project_delegation_required` with a receipt.
- **Words:** "copy for delivery", "mark delivered", DELIVERED; never "send".

### The steward lifecycle beat (a precondition of story 02)

The steward runs asynchronously: the route and the tool insert a run and return its id, then a daemon thread executes the phases (`holdspeak/web/routes/steward.py:94`; `project.py:1554-1633`). Phase 7's synchronous completion does not carry over. Before story 02 builds, a short design beat (like Phase 7's `design/grant-lifecycle-beat.md`), checked by Codex Astra, fixes:

1. **The pending handle:** the call returns `run_id` and the run's `operation_id` at once; the operation is non-terminal while the run works.
2. **Parentage:** each executed effect is a child operation of the run's operation; a scheduler-started run (`steward.trigger`, `run_due`, unattended) names its principal and authority basis (the owner's recorded policy).
3. **The terminal receipt:** exactly one per run — completed, failed, stopped or indeterminate — written in the same step that ends the run.
4. **Stop:** `project.stop_steward` is admitted; the stopped run ends with its own terminal receipt.
5. **Recovery:** after a hub restart with a run in flight, the run ends terminal (indeterminate or failed) with its receipt; no run or operation stays non-terminal. Fenced with a real restart (the Phase 7 F13 pattern).
