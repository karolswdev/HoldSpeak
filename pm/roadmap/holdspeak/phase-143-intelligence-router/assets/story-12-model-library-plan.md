### 2.2 Secret-path proof and replacement rule

The present browser flow is: password DOM control → React `keyDrafts`/`key` state → `apiFetch` JSON serialization (`web/src/lib/api.ts:44-68`) → FastAPI JSON body → `ProfileKeyService.set()` → `ProfileKeyStore`. Its final store boundary is suitable, but its browser state and the hosted path’s subsequent Settings write are not (`web/src/pages/cores/settingsModels.tsx:300-325`, `:379-438`; `holdspeak/services/profile_key_service.py:19-36`).

Story 12 therefore needs a **write-only secret handoff**, not another `StringGadget`, `SecretRow`, controlled password input, or Settings secret editor. A native password control necessarily holds typed characters while the owner is entering them; interpret the acceptance testable boundary as: no secret in React props/state, `value` attribute/serialized markup, projection, `localStorage`/`sessionStorage`, error/receipt/log, screenshot artifact, or post-confirmation DOM. Hold the value only in an uncontrolled element/ref until explicit `Connect`, submit it once through a dedicated body that is never logged, retain it only in that write-only control after a known failure, and blank it only after the service returns durable key-custody confirmation. This is the narrowest browser-realizable reading of “never DOM”; treating even the native input’s transient `value` property as forbidden would make browser key entry impossible. The exception is credential-only: it gets no speak-to-fill mic; ordinary endpoint/name/model text inputs retain the click-to-toggle mic law. (`story-12-model-library-providers.md:27`; `docs/internal/ARCHITECTURE_WEB_FRONTEND.md:101-111`; `web/src/desk/surface/gadgets.tsx:760-845`)
