## The daily experience

### First useful result

A new user can dictate and keep a sentence before configuring AI.
For architecture work, the user selects a Project and asks for one useful result.
Interview asks only questions that resolve material uncertainty.
Model or source setup opens the relevant existing control and returns to the unfinished task.

The first three supported recipes are meeting preparation, decision and commitment review, and a weekly Project update.
The user can run each recipe manually.
A kept result shows its Project, sources, coverage, and next action.

### Returning to work

The existing arrival presents up to five initial priorities.
Each priority states why it matters now and offers a lawful next action.
The rest remain accessible, with an honest total and incomplete-coverage state.
Project failures cannot turn into an apparent all-clear.

The user can resume a Thought, Interview, prepared brief, commitment, or assignment without reconstructing context.
The product distinguishes saved, running, waiting, failed, incomplete, and accepted work.

### A meeting changes the next day

A linked meeting produces reviewable decisions and actions.
Unknown owners and dates remain unknown.
Confirm, Edit, and Dismiss use the existing owning services.
An accepted commitment is visible in the Project and relevant permitted People preparation.

The next brief includes the current decision and unresolved commitment.
Opening a source shows the evidence that supported the result.
Superseded decisions remain distinguishable from current decisions.

### Conversation becomes configured behavior

“Prepare this Project every Monday” becomes a concrete configuration proposal.
It identifies the source scope, trigger, time zone, model route, output, and applicable authority.
The user can inspect the configuration and its actual run result.
An existing sufficient instruction does not acquire a redundant confirmation step.

Revisiting the conversation changes the intended configuration once.
Pause prevents future starts.
Stopping active work uses the execution owner's separate control.
Leaving an Interview does not silently install, undo, or restart anything.

### Delegated work returns with proof

An assignment binds an outcome, evidence, target, constraints, worker capabilities, limits, and acceptance checks.
The first adapter supports one supervised worker.
The result includes its artifact or diff, checks, unresolved issues, and execution receipts.
The owner can accept the result or request changes.
Worker exit alone cannot complete the related commitment.

### Unattended work earns its place

The first unattended recipes prepare a brief or examine a bounded change.
They use the same reviewed assignment and evidence contracts.
The deployment identifies which machine owns the hub and when it is available.
Missed runs, expired credentials, failed sources, and uncertain effects remain visible.

## Scope commitment

Phase 200 includes runtime and release reliability, physical capture proof, evidence semantics, daily Project work, repeatable Interview setup, supervised assignments, and bounded unattended execution.
It also includes an owner pilot, performance measurement, release packaging, and operator recovery.
These are six staged release gates inside one major phase.

The initial deployment is the Web Desk on one owner-controlled hub.
Desktop and compact browser layouts are required.
macOS physical capture is the first owner pilot.
Existing Linux support retains its release checks.
Native Swift parity, a hosted service, and a distributed multi-writer hub are separate commitments.

Additional connectors, portfolio administration, and further environment art enter only when a measured pilot gap requires them.
The existing visual character and usable companion features remain part of the product.
The scope policy concerns new delivery priority.

## Architectural direction

1. Reuse the existing citizen and domain services.
2. Treat the LLM as a proposer and drafter. Domain state and actual execution results determine completion.
3. Separate source links, supported claims, business decisions, and execution receipts.
4. Persist accepted intent before consequential dispatch.
5. Use the kernel and declared worker capabilities for actual authority and limits.
6. Make uncertainty and recovery part of each user flow.
7. Improve the shared UI library when a recurring interaction needs improvement.
8. Prove quality with real models and usefulness with real work.
