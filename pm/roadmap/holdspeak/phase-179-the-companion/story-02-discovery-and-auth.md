# HS-179-02 — Discovery and authentication

- **Project:** holdspeak
- **Phase:** 179
- **Status:** backlog
- **Depends on:** HS-179-01, HS-179-08
- **Unblocks:** HS-179-03, HS-179-04, HS-179-05, HS-179-06
- **Owner:** unassigned

## Problem

The companion must find the desktop on the LAN and authenticate with
the hub. The Bonjour mesh (mesh.py:1-45) advertises `_holdspeak._tcp`;
the companion browses for it via NWBrowser. The hub requires a token
for non-loopback connections (web_auth.py:73-89). The companion must
handle discovery failure and disconnection honestly (Article VI).

## Scope

- In:
  - NWBrowser browsing for `_holdspeak._tcp`: discover the desktop
    by name, resolve the host and port from the Bonjour TXT record.
  - Token authentication: the companion stores the hub token (entered
    once by the owner) and sends it via `X-HoldSpeak-Token` header on
    every API request.
  - Connection states: discovering, connecting, authenticated,
    disconnected, token-rejected. Each state has an honest face
    (the design story defines them).
  - Reconnection: on network change or desktop restart, the companion
    re-discovers and re-authenticates automatically.
  - Token entry: a one-time setup screen where the owner enters the
    hub token (displayed on the desktop's Settings; scannable QR
    code is a design decision).
- Out:
  - Non-LAN discovery (no cloud relay, no STUN; Article III).
  - OAuth or SSO (the hub uses a simple shared secret).
  - Multiple desktop discovery (one companion connects to one desktop).

## Acceptance criteria

- [ ] The companion discovers the desktop via `_holdspeak._tcp`
      NWBrowser browsing.
- [ ] The companion authenticates with the hub token on every API
      request (web_auth.py's `verify_web_token`).
- [ ] Connection states are honest: discovering, connecting,
      authenticated, disconnected, token-rejected (Article VI).
- [ ] Reconnection after network change or desktop restart succeeds
      without user intervention.
- [ ] Token entry is a one-time setup screen; the token persists in
      the iOS keychain.
- [ ] Verified by a test on the LAN: the companion discovers and
      authenticates with the hub.

## Test plan

- Unit: NWBrowser mock discovering a service; token authentication
  success and failure; reconnection logic.
- Integration: two devices on the same LAN; the companion discovers
  the desktop and authenticates.
- Manual: the owner's phone on his LAN discovering his desktop.

## Notes / open questions

- The hub token is currently generated by `web_auth.generate_web_token`
  (24-byte URL-safe). The companion stores it in the iOS keychain.
  A QR code on the desktop's Settings for one-tap pairing is a design
  decision (it does not change the auth model).
