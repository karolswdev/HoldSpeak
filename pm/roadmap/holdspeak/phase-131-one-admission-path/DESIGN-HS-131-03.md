# HS-131-03 design — staged projections behind the one runner

**Status:** ratified as amended by Sol  
**Decision boundary:** this design composes with `InferenceRunner`; it does not change its state machine, publish callback, closing/retry protocol, or `ClosurePersistenceError` semantics.

## 1. Kernel projection-staging protocol

Add a kernel-owned `ProjectionStager`, backed by a `kernel_projection_stages` table in the same SQLite database/connection factory as `JournalStore`.  A row contains `stage_id`, unique `invocation_id`, `operation_id` (filled from the admitted invocation), `kind`, canonical projection JSON, `result_ref`, `state`, and timestamps.  `result_ref` is `projection-stage:<stage_id>` and is the only value a migrated runner `publish(result)` callback may return.  The callback **only** calls `stage()`; it does not write an Ask result, Artifact, chat result, or any other domain object.

States are `STAGED`, `FINALIZING`, `PUBLISHED`, and `DISCARDED`.  `stage()` is idempotent on `(invocation_id, kind, canonical projection hash)`: identical retry returns the same stage; a changed payload is refused.  It commits before `publish()` returns, so the runner cannot commit a successful terminal receipt pointing at an un-durable projection.  The runner then persists its terminal receipt by its existing bounded `_persist_receipt()` path.

After `invoke()` returns a durable receipt, the service calls `finalize(invocation_id)`.  `finalize` reads the receipt and stage, atomically claims `STAGED -> FINALIZING`, materializes the registered domain projection, records its invocation ID, operation ID, and receipt ID, and commits the domain row plus `FINALIZING -> PUBLISHED` in **one database transaction**.  The response is assembled only from that committed projection.  A `succeeded` receipt is eligible only when its `result_ref` exactly equals that stage's reference.  A terminal `cancelled`, `failed`, `refused`, or `indeterminate` receipt atomically becomes `DISCARDED` without a domain object.  A missing receipt leaves the stage `STAGED` (not visible and not discarded): recovery must not invent terminal truth.

**Sol amendment:** `PUBLISHED` in this protocol is the durable **projection-stage** state, not `InferenceRunner._Active.state`.  The transaction boundary is exact: (1) `stage()` commits; (2) the callback returns `projection-stage:<stage_id>`; (3) the runner passes that exact value to `_persist_receipt()`, whose executor transaction atomically writes the terminal receipt and its `result_ref`; (4) only after that commit does the runner set its in-memory state to `PUBLISHED` and return; and (5) `finalize()` opens a separate domain transaction.  No transaction spans the stage and receipt, and none is required: their enforced order plus recovery closes that crash window.  The statement that finalization and `PUBLISHED` share one transaction applies only to the domain row and the projection-stage transition.  `finalize()` must reject a receipt with the wrong operation, invocation, outcome, or `result_ref`.

**Sol amendment:** `STAGED -> FINALIZING`, all domain inserts/updates, and `FINALIZING -> PUBLISHED` execute under one `BEGIN IMMEDIATE` transaction on one database connection.  `FINALIZING` is not committed as a lease between transactions; a crash rolls the whole unit back to `STAGED`.  Materializers may perform database work only, through the supplied transaction, and may not emit an external side effect.  A hard unique constraint on `projection_stage_id` (and the invocation/kind key where applicable) is required.  If commit succeeds but the process dies before responding, retry reads and returns the already committed projection.

At hub startup, after the journal/broker is open and before routes accept work, `ProjectionStager.recover()` scans every non-terminal stage: it finalizes a matching succeeded receipt; discards cancelled/failed/refused/indeterminate receipts; and retains an absent-receipt stage for the kernel's existing closure/reconciliation path, emitting a bounded diagnostic.  Repeated recovery and interrupted finalization are safe because the domain materializer has a unique `projection_stage_id`/invocation key and runs in the same transaction as `PUBLISHED`; a committed projection is returned, never inserted twice.

**Sol amendment:** absent-receipt stages are not immortal tombstones and may not be deleted by age alone.  Startup must run the broker's durable liveness reaper before projection recovery, and the same ordering must run periodically: while the invocation claim is live, the stage remains invisible `STAGED`; once its `execution_expires_at` passes, the kernel first writes the authoritative `indeterminate` terminal receipt, then the stager discards the stage.  A terminal operation with no receipt is a kernel reconciliation fault: keep its projection invisible, report unhealthy, and retry/repair terminal receipt closure rather than silently retaining it or inventing projection truth.  Thus retention is bounded by the admitted execution warrant plus reconciliation, and HS-131-03 owns wiring this ordering before the first migrated route opens.

Domain materializers are a kernel-owned registry invoked only by `finalize` with an unforgeable `PublicationPermit`; migrated domain repositories require that permit for runner-produced results.  The `publish` callback is restricted to `stage`, and a callback that directly calls a domain writer is prohibited and tested.  This fences the runner process-lock window rather than pretending the in-process lock itself is a transaction.

**Sol amendment:** this fence is mechanical, not a comment.  `ProjectionStager` supplies the callback accepted by the runner; migrated services may supply only a pure projection encoder, not an arbitrary publishing closure.  The permit is module-private, identity-checked, transaction-bound, and issued only inside `finalize`; missing, reused, or forged permits are refused.  The focused fence must (a) invoke each migrated callback and prove that only a stage row changes, with zero Ask/Artifact/chat rows, (b) prove each materializer refuses a missing or forged permit, (c) fail an AST/import census if migrated Ask/Recipe service code calls or imports provider builders, `run_prompt`, the legacy `RunLifecycle`, or a runner-result domain writer, and (d) run the services with direct provider/domain writers replaced by raising spies.  A Python token is not metaphysically unforgeable; these API and test fences are the enforceable contract.

**Ruled invariant:** a runner-produced domain object is visible exactly once, only from a `PUBLISHED` stage whose matching successful terminal receipt was already committed; all other stages produce zero domain objects.

## 2. Ask migration

`AskService.ask` builds its complete immutable inference payload (schema version, rendered system/user prompts, lens, grounding/context snapshot, token and temperature inputs, and resolved deployment revision) before dispatch.  It invokes the runner as the authenticated request principal with `ServiceContract.for_payload("holdspeak.ask", "1", payload)`; this is an honest service contract, not a fabricated saved definition.  The target ID is resolved once to the deployment revision before admission.  The adapter dispatches the canonical payload, and its publish callback stages an `ask-result` projection containing the present Ask result shape plus provenance and the invocation/receipt linkage.  After finalization, Ask returns the existing route shape from that projection.

Synchronous `KernelRefused` and an `InvocationOutcome(outcome="refused")` retain their machine code and cross the existing service/route typed-error path; provider failure, cancellation, and indeterminate outcomes do likewise and never mint an answer projection.  The existing cancellation surface addresses the invocation ID through `runner.cancel`; its child lifecycle remains exactly the Round-13 ruling: the elected cancellation performer persists its own child receipt before any cancellation disposition is observable, and a closure-persistence failure wins over late publication.

**Sol amendment:** `holdspeak.ask@1` is a named schema constant, not an inline string that can drift.  The canonical payload contains `schema_version: 1` and the exact resolved deployment revision; any semantic payload change requires an explicit contract/schema-version decision and compatibility test.  Resolve target ID to one immutable deployment revision before constructing and hashing the payload.  One typed outcome mapper handles both pre-invocation `KernelRefused` and returned terminal outcomes without collapsing their machine codes into generic `inference_failed`; when an invocation exists, its invocation ID, operation ID, receipt, egress facts, and result reference travel through the existing response/error context.  The authenticated request principal is the runner principal.  Recipe's legacy lifecycle and Ask/Recipe provider exception handlers may not manufacture a second invocation, receipt, or outcome.

**Sol amendment:** the cancellation race is stated in runner terms.  Cancellation elected before `PUBLISHING` prevents the callback and therefore creates no stage.  Once `stage()` is running, the runner is already `PUBLISHING`; a later cancellation truthfully returns `completed` and cannot replace successful publication.  If receipt closure fails or the durable liveness reaper wins after staging, the stage remains invisible and is later discarded from that authoritative non-success receipt.  Recovery still defensively discards a matching `cancelled` receipt, but tests must not fabricate that as the only proof of the real runner race.  Round-13 cancellation-child receipt ordering and `ClosurePersistenceError` precedence remain unchanged.

**Ruled invariant:** every Ask answer has one `holdspeak.ask@1` invocation, a payload hash matching dispatched bytes, and a finalized projection referring to that invocation and its receipt; refusal or cancellation has no answer projection.

## 3. Recipe run and chat migration

Recipe run resolves the saved recipe first and submits `SavedDefinition(ref="recipe:<id>", revision=<persisted recipe.last_modified>)`; the runner's existing live-revision check remains authoritative.  Its canonical payload preserves the current rendered prompts, variables, source/grounding snapshot, limits, and the deployment revision selected by the target ID.  Its staged `recipe-run` projection owns the current Artifact materialization and existing result fields.  Target ID still selects placement; a model name is descriptive validation only and cannot select another target.

Each Recipe chat model call is one runner invocation using the same saved-definition origin and a canonical payload containing the bounded history and assembled context.  A standalone chat has no synthetic parent.  If chat is performed inside an existing outer Recipe run, its `InvocationRequest.parent_operation_id` is that outer run's operation ID; otherwise it is empty.  A staged `recipe-chat-result` projection supplies the unchanged chat response after the terminal receipt.  No chat turn executes a provider directly.

**Sol amendment:** the saved origin is exactly `SavedDefinition(ref=f"recipe:{recipe_id}", revision=str(recipe.last_modified))`, resolved before admission; do not retain the old `persona:` reference or `created_at`/`"unversioned"` fallback.  The migrated run removes `RunLifecycle` rather than nesting the runner inside it.  Its existing Artifact write occurs only in the `recipe-run` materializer after the runner receipt.  Target ID is resolved once to the admitted deployment revision; model/default-model fields may validate or describe the selected target but never participate in selection.

**Sol amendment:** an unparented chat turn is a legitimate authenticated, owner-admitted root invocation, not an orphan: it has one root operation and terminal receipt for that turn.  `parent_operation_id` may come only from trusted in-process outer-run context, never a client-supplied field; when present it must be the live outer Recipe run operation and pass the runner's normal owner/causation checks.  Add no synthetic parent merely to make the graph look connected.  The same typed outcome mapper used by Ask preserves pre-admission refusal, terminal refusal, provider failure, cancellation, and indeterminate outcomes with zero chat projection on non-success.

**Ruled invariant:** each Recipe model dispatch has exactly one invocation with the persisted recipe revision, and its placement is fixed by the admitted target ID, never by a model name or a later target mutation.

## 4. Non-changes

This adds no UI, no route redesign, and no new placement control.  Ask, Recipe run, and Recipe chat keep their domain result shapes and external route contracts; projection linkage is stored natively and exposed only where existing metadata already permits it.  The runner remains unchanged, including its publish-callback order and all cancellation-child outcome rules.

**Ruled invariant:** HS-131-03 replaces caller-owned model execution/publication, not caller-facing contracts or runner policy.

## 5. Required tests before implementation closes

- `test_projection_stage_precedes_success_receipt` — callback stages durably before the runner can persist its successful receipt.
- `test_receipt_atomically_carries_exact_projection_stage_ref` — the executor's terminal transaction stores the exact staged reference; a wrong operation/invocation/reference cannot finalize.
- `test_receipt_closure_exhaustion_leaves_stage_invisible` — all bounded receipt retries fail, `ClosurePersistenceError` wins, and no projection becomes visible.
- `test_recover_crash_after_stage_before_receipt_keeps_result_invisible` — an absent-receipt stage survives recovery without a domain object or duplicate while its warrant is live.
- `test_expired_absent_receipt_is_reaped_indeterminate_then_discarded` — startup/periodic ordering terminalizes the expired invocation before discarding its stage; no age-only deletion occurs.
- `test_terminal_operation_without_receipt_blocks_projection_and_reports_unhealthy` — a reconciliation fault never publishes or silently becomes an immortal diagnostic.
- `test_recover_success_receipt_finalizes_once` — startup finalizes an orphaned successful stage once and links its receipt.
- `test_runner_cancellation_races_the_stage_boundary_truthfully` — cancellation before `PUBLISHING` creates no stage; cancellation after staging reports `completed`; an authoritative non-success receipt discards an invisible stage.
- `test_recover_cancelled_stage_discards_projection` — defensive recovery of a matching cancelled terminal receipt leaves no result object.
- `test_recover_failed_refused_indeterminate_stages_discard` — every non-success terminal outcome is non-publishable.
- `test_interrupted_projection_finalization_is_idempotent` — rollback during the one finalization transaction resumes without duplicate Artifact/Ask/chat records.
- `test_concurrent_finalize_and_lost_response_return_one_projection` — concurrent finalizers and retry after commit produce and return one domain row.
- `test_materializer_transaction_rollback_has_no_external_effect` — a materializer failure rolls back both domain writes and stage state and emits no external side effect.
- `test_stage_payload_conflict_is_refused` — one invocation cannot replace its staged projection with changed content.
- `test_publish_callbacks_and_permits_enforce_the_bypass_fence` — callbacks change only the stage table, missing/forged/reused permits fail, raising spies see no direct domain/provider call, and the AST/import census has no forbidden seam.

- `test_ask_contract_payload_change_requires_version_decision` — the contract fixture fails on unreviewed semantic payload drift.
- `test_recipe_run_uses_exact_saved_revision_and_staged_artifact` — run uses `recipe:<id>` at exact `last_modified`, has no fallback/legacy lifecycle, and finalizes one Artifact after receipt.
- `test_recipe_chat_root_and_trusted_outer_parent` — each standalone turn is one authenticated root invocation; trusted outer context supplies the exact parent; client parent injection and wrong/dead parents are refused.
- `test_pre_admission_and_terminal_outcomes_preserve_typed_route_contract` — synchronous `KernelRefused` and refused/failed/cancelled/indeterminate outcomes keep distinct machine codes and linkage, with no projection.
- `test_cancellation_child_receipt_precedes_service_disposition` — the migrated cancellation surface preserves the Round-13 child-outcome mapping and closure-failure precedence.
- `test_target_mutation_or_model_mismatch_cannot_retarget_admitted_recipe_or_ask` — admitted deployment identity remains immutable.

**Ruled invariant:** implementation is not complete without focused proof of every listed crash state and of one-runner-only Ask, Recipe run, and Recipe chat dispatch.

## Sol design ruling — 2026-08-10

**Verdict: ratify as amended.**  The protocol now closes all five required windows without contradicting the ratified runner: staging commits before terminal closure; a crash before the receipt leaves an invisible stage governed by the invocation warrant and liveness reaper; cancellation before publication creates no stage while cancellation after staging cannot rewrite `PUBLISHING`; interrupted finalization rolls back one transaction; and unique stage/domain keys make recovery and lost-response retry idempotent.  The terminal receipt's stage reference is written in the executor's own atomic receipt transaction, while domain finalization is deliberately a later transaction after that receipt is durable.

**Sol amendment:** ratification is conditional on implementing the exact transaction boundary, bounded absent-receipt reconciliation, mechanical bypass fence, truthful Ask schema/version and typed-outcome mapping, exact Recipe revision/root-parenting rules, and every expanded test obligation above.  Silently retaining absent-receipt stages forever, permitting arbitrary service-owned publish callbacks, nesting the legacy Recipe lifecycle, or proving cancellation only with a fabricated post-stage cancelled receipt voids this ruling.

## Sol implementation review — 2026-08-10

**Verdict: do not ratify.**  The central staging protocol is credible, and the focused command passed twice under an isolated `HOME` (`91 passed` in 45.14s, then `91 passed` in 21.64s), but the implementation does not yet satisfy the amended design's startup recovery, mechanical fence, typed route, cancellation-surface, or test-floor conditions.  The orchestrator's separate real-LAN walk is not a gate for this ruling.

### Amendment-by-amendment ruling

1. **Stage before receipt — passes.** `stage()` commits before its callback returns; the runner carries that exact `projection-stage:<id>` through its bounded receipt write and only then returns; services finalize afterward.  Finalization rejects a non-success or mismatched result reference, and checks the stage operation against the invocation-bearing operation.
2. **One `BEGIN IMMEDIATE` finalization unit — passes in implementation, proof incomplete.** Claim, domain writes, and `PUBLISHED` occur on one connection in one transaction; rollback restores `STAGED`; unique projection-stage/invocation keys and persisted `final_result_json` make a lost response retry idempotent.  The production-materializer rollback test is real.  The alleged concurrency proof, however, finalizes two different invocations, not two contenders for the same stage, and does not simulate a lost response.
3. **Bounded absent-receipt recovery — blocker.** The liveness reaper now genuinely runs before recovery in kernel construction and on the web server's one-second loop.  That materially and partially discharges the HS-131-02 reservation: expired claims can now receive authoritative `indeterminate` receipts before stages are discarded.  But startup recovery runs before Ask/Recipe materializers are registered.  A durable succeeded `ask-result` stage therefore aborts `_configure()`/hub construction with `KernelRefused("projection_materializer_unknown")`; I reproduced exactly that state.  Also, `terminal_operation_without_receipt` is retained only in an internal return/property that startup and the periodic loop ignore: it is neither emitted into health nor repaired.
4. **Mechanical bypass fence — blocker.** AST/token checks and missing/forged permit checks exist.  The required raising-spy proof is missing.  There is also no focused proof that each real migrated callback, stopped immediately after callback execution, changes only the stage table; reused permits are not tested.  Passing services through a working provider engine is not the ruled raising-spy test for forbidden direct provider/domain calls.
5. **`holdspeak.ask@1` and typed outcomes — Ask passes; shared mapping/Recipe route block.** Ask uses named contract/schema constants, resolves one immutable deployment revision before hashing, and dispatches the canonical bytes through the runner.  Pre-invocation and returned outcomes are not collapsed to `inference_failed`.  But Ask and Recipe duplicate rather than share the ruled typed mapper; Recipe omits `result_ref` from returned outcome context.  More seriously, Recipe's route ignores the mapper's `context.status`: an unlisted synchronous kernel refusal code defaults to HTTP 500 instead of the typed 409 path.
6. **Cancellation/staging truthfulness — runner race passes; product surface blocks.** The real migrated Ask race proves cancellation after committed staging observes `PUBLISHING`, returns `completed`, and preserves one successful projection.  The inherited runner suite proves the pre-publish race, child-receipt-before-disposition ordering, and `ClosurePersistenceError` precedence.  But neither migrated service exposes or retains a runner cancellation surface.  The existing `/api/invocations/{id}/cancel` path accepts only legacy `inference.run`, not these `inference.invoke` operations, so cancellation is not propagated through the existing service/route boundary as required by the story.
7. **Exact Recipe revisioning — passes in implementation, proof should be tightened.** Run and chat use exactly `SavedDefinition(ref=f"recipe:{recipe_id}", revision=str(recipe.last_modified))`; target resolution precedes payload construction; model text does not select placement; `RunLifecycle`, `persona:`, and revision fallbacks are gone; Artifact creation occurs only in the finalizer.  The focused test should inspect the admitted origin revision rather than merely assert that `last_modified` is nonempty.
8. **Recipe chat parent ruling — root-only deferral accepted.** There is no trusted production outer-run context carrier or caller today.  Accepting only authenticated root chat invocations is the complete truthful behavior for HS-131-03 and prevents client parent injection.  The positive trusted-parent path is deferred, visibly, to whichever of HS-131-04 Sequence/Workflow or HS-131-05 Workbench first introduces a real in-process outer-run context.  That story must add the positive live-parent proof plus wrong/dead/foreign-parent refusals; this is not a blocker here.

### Test-floor ruling

Of the four late tests, the materializer rollback and post-stage cancellation tests force what they claim.  The concurrency test exercises simultaneous SQLite writers for two different stages, not same-stage concurrent finalization or lost-response replay.  The Ask contract test freezes field names and Python value types, but changing semantic prompt content or another same-typed contract value does not fail its shape hash.  The broader ruled floor is also still absent for successful startup recovery, expired absent-receipt reaping, surfaced terminal-without-receipt health, closure-exhaustion invisibility, every non-success recovery outcome, wrong receipt linkage, reused permits, and migrated-service raising spies.

**Blockers to a new sitting:** register all production materializers before startup recovery and surface reconciliation faults; complete the mechanical fence including raising spies; provide a real cancellation path for migrated invocation IDs; fix the shared Recipe typed route mapping/linkage; and land tests that exercise the named crash/race states rather than proxies.

## Sol final ratification pass — 2026-08-10

**Verdict: do not ratify.** Round 2 resolves four implementation blockers and materially improves the proofs, but the product cancellation path still constructs a fresh service and therefore a fresh runner for every request. The cancel route cannot see the active invocation registry owned by the service that started Ask or Recipe. This is the same defect the service-level test found, one layer higher, and it leaves the cancellation acceptance criterion false. The real-LAN walk remains under the orchestrator's hand and does not change this ruling.

### Prior blockers, rechecked

1. **Startup recovery — resolved.** `holdspeak/kernel/runtime.py:94-105` creates the stager, registers Ask and Recipe materializers, and only then calls `recover()`. `tests/unit/test_hs13103_remaining_obligations.py:332-347` boots through `_configure()`, finalizes the orphaned succeeded Ask stage, boots a second time, and proves one domain row.
2. **Reconciliation health — resolved.** `holdspeak/kernel/projection_stager.py:158-185` retains current terminal-operation-without-receipt faults, and `holdspeak/services/desk_service.py:49-52` reports them as `unhealthy`. The focused health proof at `tests/unit/test_hs13103_remaining_obligations.py:350-365` forces the malformed durable state before reading Desk health.

6. **Cancellation surface — unresolved at the route boundary.** A single `AskService` or `RecipeService` correctly retains one runner (`holdspeak/services/ask_service.py:46-51`, `holdspeak/services/recipe_service.py:33-45`), and their `cancel()` methods use it (`ask_service.py:159-164`, `recipe_service.py:134-139`). But `holdspeak/web/routes/primitives/ask.py:28-30,47,60-63` calls a factory that returns a new service for both the run and cancel requests. Recipe does the same at `holdspeak/web/routes/primitives/recipes.py:23-25,100,153-156`. The route proof at `tests/unit/test_hs13103_remaining_obligations.py:490-500` tests only unknown IDs and accepts `pending`; it cannot detect that a live invocation is being cancelled through the wrong runner. The router must retain a shared service/runner (or the active registry must move to an intentionally shared owner), and a live route-level cancellation race must prove it.

### Shared runner and principal-context ruling

The `ContextVar` mechanism itself is sound for a retained service instance. Each service sets and resets the acting principal around the synchronous runner call; Python contexts isolate values across OS threads and asyncio tasks. `InferenceRunner.invoke()` and `cancel()` read the provider at call entry (`holdspeak/kernel/inference_runner.py:48,166-168`), so neither can observe another concurrent request's principal. The deadline watchdog deliberately captures the invoking principal and uses `_cancel_internal()` (`:186`), while an early external cancellation stores its own principal with the pending invocation (`:50-58,184-185`). There is no cross-principal leak in these paths. The hole is lifetime, not `ContextVar`: route factories discard the runner that owns `_active` and send cancellation to another runner.

### Three proof spot-checks

- **Startup finalize-once:** forces the production boot seam and second-boot idempotency; it proves the claimed ordering and exactly-once materialization.
- **Same-stage contention:** holds the real Ask materializer inside the transaction, starts a second finalizer for the same invocation, then proves both responses match and only one `ask_results` row exists. This now forces the claimed contention/replay behavior.
- **Service cancellation:** truthfully proves post-stage cancellation on the same service instance returns `completed` and preserves one projection. It does not prove the HTTP surface, because the routes instantiate another service. The separate route-delegation test's unknown IDs mask that defect.

### Final acceptance sweep

Ask, Recipe run, and Recipe chat dispatch through `InferenceRunner`; Ask uses the named `holdspeak.ask@1` service contract and immutable payload hash; Recipe uses `recipe:<id>` with the persisted `last_modified`; successful native projections carry invocation, operation, receipt, and stage result references; target identity is captured as a deployment revision; and typed non-success mapping no longer loses Recipe status or `result_ref`. Ask's named model-mismatch refusal remains covered by the route suite. However, authenticated cancellation is not propagated to a live migrated invocation through the actual route boundary, so acceptance criterion 5 is not met.

The expanded design test floor also remains incomplete for stage-specific receipt-closure exhaustion, expired absent-receipt reaping through discard, all non-success recovery outcomes, wrong receipt linkage, and a true service-level forbidden-seam raising-spy run. These are named reservations that must be closed or explicitly amended before ratification.

## Sol targeted re-verification — 2026-08-10

**Verdict: ratify with named reservations.** The route-lifetime blocker is resolved. `kernel/runtime.py` constructs exactly one `InferenceRunner` for each configured broker and supplies the existing request-principal `ContextVar`; both migrated services retain `broker.inference_runner`, so constructing another service for a later HTTP request no longer loses the active invocation registry. A production census finds no other `InferenceRunner(...)` construction. `_principal` defaults to `UNAUTHENTICATED`, whose `PrincipalKind.NONE` is refused by broker admission as `principal_authentication_required`; an omitted service wrapper therefore cannot inherit owner authority or escalate.

The replacement cancellation proof forces the defect from the prior pass rather than its proxy. It pauses a real Ask invocation after the stage commits while the shared runner is `PUBLISHING`, constructs a second `AskService` against the same broker, and cancels through that second instance. The result is `completed`, the invocation finishes successfully, exactly one Ask projection is published, and no cancellation child operation is invented. Because the production route factories construct their services against the broker returned for the same database singleton, this is the cross-request lifetime seam that previously failed. The older unknown-ID route delegation check remains weak by itself, but it no longer carries the lifetime claim.

Against the story's chartered acceptance criteria, no blocker remains: Ask, Recipe run, and Recipe chat use the broker-owned runner; live cancellation now crosses per-request service construction; authenticated principal context is scoped and reset; and the inspected projection finalizer enforces successful receipt linkage before publication while discarding non-success receipts. The five proof gaps named in the prior pass are **non-blocking, named design-floor reservations for the sitting**, not HS-131-03 acceptance failures:

1. Add a true migrated-service raising-spy test for both Ask and Recipe with every forbidden direct provider/domain seam replaced by a raising spy. The current AST/import fence, callback table-delta proof, production construction census, and service execution proofs establish the chartered one-runner behavior; the exact spy topology remains stronger negative proof.
2. Add a stage-specific receipt-closure-exhaustion test. Generic runner closure precedence and absent-receipt stage invisibility are already proved separately; one composed test should force every bounded receipt write to fail after a real migrated stage commits.
3. Add an expired-stage end-to-end proof that observes reaping write `indeterminate` and then observes recovery discard the stage. The production ordering is wired (`recover()` reaps before scanning), but this exact transition chain is not focused in the requested suite.
4. Parameterize recovery across `cancelled`, `failed`, `refused`, and `indeterminate` receipts. The implementation uses one `_NON_SUCCESS` discard branch, and service/route outcome behavior is covered; the exhaustive recovery matrix remains proof debt.
5. Add negative linkage cases for wrong invocation/operation association and wrong `result_ref`. `finalize()` contains both guards and positive native linkage is covered, but the focused suite does not force each guard.

These reservations should be recorded at the sitting and closed in the projection-protocol proof ledger before the phase's one-path fence/closeout; they do not justify keeping this migration story open absent a newly demonstrated product defect.
